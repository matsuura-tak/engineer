# 第1部 発見（何を、なぜ作るか）

## 1. 紹介文
すでにコードを書いているエンジニアが、3分以内の自己診断（8問）で今の段階と目標を伝えると、翌日から毎日「今日やる学習」が1つだけ、15分で終わる形で出ます。100以上の技術が並ぶ学習の地図（roadmap.sh）や、積んだままの教材から「どれをやるか」を選ぶ時間が、毎日0分になります。英語の壁、ハート、広告、ネット接続はありません。難しすぎ・簡単すぎの申告が2回続けば次の日から段階が変わるので、同じ段階の問題を繰り返されることがありません。

## 2. 中心の Job
- Job ストーリー（1つだけ）：平日の朝や通勤中に15分空いたとき、自分の今の段階と目標に合った学習を1つだけ選んで始めたい。そうすれば何をやるか迷う時間をなくし、毎日続けられる。
- 機能の面：15分で終わる学習が1つ決まる。　気持ちの面：「今日も前に進んだ」と感じる。　人の目の面：同僚や面接で「最近学んだこと」を具体的に言える。

## 4. 4つの力
| 今の状況の押し | 新しいものの引き | 乗り換えの不安 | 今の習慣 |
|---|---|---|---|
| 学ぶべきことが多すぎて、どれから手を付けるか決まらないまま日が過ぎる（E-1）。コースは段階に合わない（E-3、E-4） | 診断3分、毎日1つ、15分で終わる。段階に合わせて変わる。日本語、オフライン、無料 | 「自己申告の診断で本当に合う課題が出るのか」「課題が尽きたら終わりでは」「また続かないのでは」 | 気が向いたときに記事を読む、Udemy を積む、ChatGPT に聞く、何もしない |

- 不安と習慣を下げる手当て（9 か 11 に入れる）：診断の直後に1件目を出して「合うか」をその場で確かめられる（AC-2）。難しすぎ・簡単すぎの申告で段階が動く（AC-6）。毎日決まった時刻の通知を選べ、断っても使える（AC-11、AC-12）。課題が尽きたら隠さず知らせ、診断のやり直しへ案内する（AC-8）。

## 5. 機会と解決
- 根（成果）：出した学習に対する完了率
- 機会（顧客の言葉で）：
  - O-1 「何を学ぶべきか決められず、結局何もしない日が多い」（解き方：処方する／地図を見せる／AI に聞かせる）
  - O-2 「自分の段階に合わない課題が出て、つまらないか、つらい」（解き方：自己診断で決める／申告で動かす／テストで測る）
  - O-3 「始めても、翌日には忘れて続かない」（解き方：通知／連続記録／カレンダー登録）
  - O-4 「他で学んだことが、学習の計画に反映されない」（解き方：手入力／外部サービス連携）。002 以降に回す
- 選んだ機会と理由：O-1 を中心に、O-2 と O-3 を最小の手当てで支える。O-1 が根の指標に直接効き、競合の不満（E-1、E-2）が最も集中しているため。

## 8. 推奨
- 形を変えて作る：依頼どおり「診断と今日の学習」を作るが、形を2つ変える。(1) 教材を抱えず、同梱した「15分の課題」を1つ処方する形にする。(2) 生成 AI とトレンド取り込みは v1 に入れず、002 以降でバックエンドの要否と一緒に決める。
- いちばん強い反論：課題の品質と量（領域 × 3段階 × 14日分）が勝負で、それを書くのはアプリでなく人であり、3週の枠の中で書き切れない、または書けても「役に立った」が付かない可能性がある。これが外れたら、どれだけ画面がよくても完了率は上がらない。
- 作らない場合に起きること：対象の人は roadmap.sh や ChatGPT で毎回自分で選び続け、「決められない日」が残る。このアプリの以降の機能（他で学んだことの反映、トレンド）は土台がなく始められない。

## 10. やらないこと（非目標）と、はまりやすい所
- やらないこと（理由を1行ずつ）：
  - アプリ内でコードを書く・実行する：教材を抱える形になり、Mimo や Sololearn と同じ土俵になる。
  - 生成 AI による課題の生成：端末内 LLM は対象機種を狭め、外部 API はバックエンドが要る（S-2、S-3）。
  - トレンドの取り込みや課題のネット経由の更新：ネット接続とホスティングが要る。002 以降で決める。
  - 他で学んだことの記録と反映（O-4）：Job が2つ目になる。002 で扱う。
  - アカウント、ログイン、端末間の同期：v1 はサーバーを持たない。
  - 連続記録（ストリーク）、ハート、広告、課金：競合の不満の中心（E-4、product.md）。
  - 課題の中身の正しさの自動判定：自己申告にする。実力テストは v1 で扱わない。
- はまりやすい所と避け方：
  - 診断の質問を増やしたくなる：8問の上限を AC-1 に固定し、足すなら他を削る。
  - 課題集の件数が足りないまま出す：AC-8 で尽きたときの表示を用意し、件数は G3 の検証で数える。
  - 「段階」の規則を複雑にしたくなる：2回連続の規則だけにし、変えるなら公開後の数字で決める。

## 11. 受け入れ条件
画面名と文言キーは designer が design/001-daily-learning.md で確定する。ここでは状態の名前と文言キーを仮に置く（`diagnosis.*`、`task.*`、`settings.*`）。

- AC-1：初回起動で自己診断が始まり、8問以内で終わる
  - Given：アプリを初めて起動した（保存データなし）
  - When：起動が終わる
  - Then：状態 `diagnosis.start` が表示され、質問の総数が 8 以下で、進み具合が「n / 8」の形で出る
  - 確かめ方：画面のテスト（質問数を数える）とスクリーンショット
  - 効く機会：O-2
- AC-2：診断を終えると、その場で今日の課題が1件出る
  - Given：8問すべてに答えた
  - When：最後の回答を確定する
  - Then：1秒以内に状態 `task.today` が表示され、課題は1件だけで、その課題の領域は診断で選んだ目標の領域と一致し、段階は自己評価と一致する
  - 確かめ方：画面のテスト（目標の領域と段階を変えた3通りで、出た課題の領域と段階が一致する）
  - 効く機会：O-1、O-2
- AC-3：課題は4要素をすべて持つ
  - Given：状態 `task.today` が表示されている
  - When：課題を見る
  - Then：題名、なぜ今これか、やり方、完了の目安の4要素が空でなく、完了の目安に書かれた所要時間は 15 分以下である
  - 確かめ方：同梱タスク集の全件を読む単体テスト（4要素が空でない、所要時間 ≤ 15）と画面のテスト
  - 効く機会：O-1
- AC-4：完了すると、その日はもう課題が出ない
  - Given：状態 `task.today` で課題が出ている
  - When：「完了」を申告する
  - Then：状態 `task.done` になり、同じ日（端末の日付）に再起動しても状態 `task.done` のままで、新しい課題は出ない
  - 確かめ方：画面のテスト（完了 → 再起動）
  - 効く機会：O-1
- AC-5：翌日には前日と異なる課題が出る
  - Given：前日に課題を完了した
  - When：端末の日付が翌日になって起動する
  - Then：状態 `task.today` になり、課題の ID が前日の ID と異なり、過去に完了した課題の ID のどれとも一致しない
  - 確かめ方：画面のテスト（日付を進められるテスト用の時計を使う）
  - 効く機会：O-1、O-3
- AC-6：「難しすぎ」または「簡単すぎ」が2回連続すると段階が1つ動く
  - Given：段階が「中」で、前回の課題に「難しすぎ」と申告した
  - When：今回の課題にも「難しすぎ」と申告する
  - Then：翌日の課題の段階は「初」になる。逆に「簡単すぎ」が2回連続なら「上」になる。1回だけなら段階は変わらない。「初」で「難しすぎ」が続いても「初」のまま
  - 確かめ方：段階を決める関数の単体テスト（4通り）と画面のテスト（1通り）
  - 効く機会：O-2
- AC-7：完了後に「役に立った」を1回だけ聞き、答えを保存する
  - Given：「完了」を申告した
  - When：「役に立った」か「立たなかった」を選ぶ
  - Then：状態 `task.done` に戻り、同じ課題について再び聞かれず、答えが完了した課題の一覧にその課題と一緒に残る
  - 確かめ方：画面のテスト
  - 効く機会：O-1
- AC-8：課題が尽きたら隠さず知らせ、診断のやり直しへ案内する
  - Given：目標の領域と現在の段階の課題をすべて完了した
  - When：翌日に起動する
  - Then：状態 `task.exhausted` が表示され、文言キー `task.exhausted.message` と、診断のやり直しに進む操作が1つある
  - 確かめ方：画面のテスト（テスト用のタスク集を 2 件にして起動する）
  - 効く機会：当たり前（空）
- AC-9：保存に失敗しても入力は失われない
  - Given：診断の途中で、保存先への書き込みが失敗する（テストで失敗を注入する）
  - When：回答を確定する
  - Then：文言キー `error.save.message` が表示され、それまでの回答が画面に残り、やり直しの操作が1つある
  - 確かめ方：画面のテスト（保存の失敗を注入）
  - 効く機会：当たり前（エラー）
- AC-10：オフラインで AC-1〜AC-8 がすべて動く
  - Given：端末が機内モードである
  - When：AC-1〜AC-8 の操作を行う
  - Then：AC-1〜AC-8 の Then がすべて満たされ、ネットワークへの送信は計測のイベント以外に 0 件である
  - 確かめ方：画面のテスト（機内モード）とネットワークのログ
  - 効く機会：当たり前（オフライン）
- AC-11：通知を断っても課題は出る
  - Given：通知の許可を求める画面で「許可しない」を選んだ
  - When：翌日に起動する
  - Then：状態 `task.today` が表示され、設定の画面に文言キー `settings.notification.denied` と、端末の設定を開く操作が1つある
  - 確かめ方：画面のテスト（権限を断った状態）とスクリーンショット
  - 効く機会：当たり前（権限を断ったとき）、O-3
- AC-12：通知を許可すると、選んだ時刻に1日1回だけ届く
  - Given：通知を許可し、時刻を 07:30 に設定した
  - When：翌日の 07:30 になる
  - Then：通知が1件届き、その日に2件目は届かず、通知の本文はその日の課題の題名である
  - 確かめ方：画面のテスト（予約された通知の数と時刻を読む）
  - 効く機会：O-3
- AC-13：診断をやり直しても完了の履歴は残る
  - Given：完了した課題が 3 件ある
  - When：設定から診断をやり直し、8問に答える
  - Then：状態 `task.today` に新しい課題が出て、完了した課題の一覧は 3 件のままである
  - 確かめ方：画面のテスト
  - 効く機会：O-2
- AC-14：起動から課題の表示まで2秒以内
  - Given：診断済みで、アプリが終了している
  - When：起動する
  - Then：起動から状態 `task.today` の表示まで 2 秒以内である（iPhone 12 相当のシミュレーターで 5 回計測し、すべて 2 秒以内）
  - 確かめ方：画面のテスト（計測）
  - 効く機会：当たり前
- AC-15：データの全削除で初回の状態に戻る
  - Given：診断済みで完了の履歴がある
  - When：設定の「すべてのデータを削除」を確定する
  - Then：保存データが 0 件になり、再起動すると状態 `diagnosis.start` が表示される
  - 確かめ方：画面のテスト
  - 効く機会：当たり前
- AC-16：いちばん大きい文字でも文言が切れない
  - Given：Dynamic Type が AX5 に設定されている
  - When：`diagnosis.start`、`task.today`、`task.done`、`task.exhausted` を表示する
  - Then：4つの状態で、文言の切り詰め（「…」）が 0 か所で、操作できる要素が画面外に出ない
  - 確かめ方：スクリーンショット（AX5）とアクセシビリティ監査
  - 効く機会：当たり前

## 12. 非機能要件
- 速さ：起動から課題の表示まで 2 秒以内（AC-14）。診断の各質問の切り替えは 0.5 秒以内。
- オフラインや通信エラーのとき：すべての機能が端末内で動く（AC-10）。計測のイベントは送れないときに端末に溜め、次回の接続時に送る。
- セキュリティとプライバシー：扱う個人データは、自己診断の回答（目標の領域、経験年数、自己評価、使える時間）、課題の完了と申告の履歴、通知の時刻。すべて端末内に保存し、外部に送るのは 15 のイベントだけ。アカウントなし。同意が要るデータは扱わない。削除は AC-15。
- アクセシビリティ：Dynamic Type（AX5 まで）、VoiceOver（すべての操作にラベル）、コントラスト（designer が G1 で3通りを示す）。
- 言語：日本語（主）、英語（副）。課題集は v1 では日本語のみ。英語の課題集は 18 の Q2。
