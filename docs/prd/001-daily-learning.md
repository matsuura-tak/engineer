# 第1部 発見（何を、なぜ作るか）

## 1. 紹介文
コードを書いたことがない人から現役のエンジニアまで、URL を開いて3問（1分以内）の自己診断に答えると、その日から毎日「今日の一手」が1つ、15分以内（初級は10分以内）で終わる形で出ます。1 つの一手は、図つきの短い説明（300 字以内）を読み、3 択の問題に 3 問、タップで答える形です。選んだ瞬間（0.3 秒以内）に合っていたかが分かり、選んだ答えに合わせた説明（なぜ違うか、どう考えればよいか）がその場で出ます。書く欄も点数もなく、案内役のキャラクターが正解でも不正解でも一緒に進みます。インストール、アカウント登録、料金はなく、ブラウザを開いてから最初の課題が出るまで2分以内です。96本の地図が並ぶ roadmap.sh や、積んだままの教材から「どれをやるか」を選ぶ時間が毎日0分になります。終えると、その課題でいちばん大事な「ひとこと解説」が開き、累計の件数が1つ増えます。時間がある日は「次の一手」で続けて進め、段階の課題をやり切ると次の段階へ進めます。3 問中 3 問正解が 3 件続けば次の課題から段階が上がり、1 問以下が 2 件続けば下がります。連続記録を失う仕組み、ハート、広告、英語の壁はありません。入力したデータはあなたのブラウザの中だけに保存され、外には送りません（ページを配る GitHub Pages が接続の記録として IP アドレスを保存するだけです）。

## 2. 中心の Job
- Job ストーリー（1つだけ）：学びたい気持ちはあるが何から手を付けるか迷うとき（通勤の15分、休日にまとめて進めたい日のどちらも）、今の自分の段階に合った学習を1つずつ、迷わずに始めたい。そうすれば決められない日をなくし、毎日続けられる。
- 機能の面：段階に合う学習が1つ決まり、答えが合っていたかがその場で分かり、やりたい日はその場で次に進める。　気持ちの面：「今日も前に進んだ」「分かった」と感じ、終えた直後に小さな発見がある。間違えても責められない。　人の目の面：同僚や面接で「最近学んだこと」を具体的に言える。

## 4. 4つの力

## 5. 機会と解決
- 根（成果）：出した学習に対する完了率
- 機会（顧客の言葉で）：
  - O-1 「何を学ぶべきか決められず、結局何もしない日が多い」（解き方：処方する／地図を見せる／AI に聞かせる）
  - O-2 「自分の段階に合わない課題が出て、つまらないか、つらい」。未経験なら「用語も環境も分からない」（解き方：自己診断で決める／申告で動かす／正誤で動かす／本文で用語を説明する）
  - O-3 「始めても、翌日には忘れて続かない」（解き方：ホーム画面に置く／Web Push／カレンダー登録／連続記録／累計と節目）
  - O-4 「他で学んだことが、学習の計画に反映されない」（解き方：手入力／外部サービス連携）。002 以降に回す
  - O-5 「やる気がある日に 1 問で止められて物足りない。終えても何も起きず、面白くない」（FB-2、FB-3。解き方：同じ日に続けて進める／完了の直後に解説と累計を見せる／段階の修了と進級／連続記録／キャラクター）
  - O-6 「読んで書くだけの課題は退屈で、自分の答えが合っていたのか分からない。文字だけだと頭に入らない」（FB2-1〜FB2-5。解き方：選択式でその場で正誤と説明／自己採点の表を見せる／AI に添削させる／図を付ける／キャラクターが反応する）
- 選んだ機会と理由：O-1 を中心に、O-2、O-3、O-5、O-6 を最小の手当てで支える。O-1 が根の指標に直接効き、競合の不満（E-1、E-2、E-6）が最も集中しているため。O-6 は Takuma の FB2 で加え、研究（E-22）と JP のレビュー（E-26、E-27）で「説明つきの即時の返し」が効き、「笑うキャラクター」「曖昧な説明」が副作用になると分かったので、その形に限る。

## 8. 推奨
- 形を変えて作る（r12）：r11 の「診断と今日の学習」を土台に、課題の型を「選んで学ぶ」に変える。(1) 1 件＝図つきの導入（300 字以内）→ 3 択 × 3 問 → まとめ。答えを書く欄は置かない。(2) 1 問ごとに、選んだ瞬間に正誤と「選んだ選択肢の説明」を出す。不正解なら正解の説明も出す。選び直しはしない。(3) 段階は正誤で動かす（下げ 2 件、上げ 3 件）。自己申告は「今日はやめておく」だけ残す。(4) 図は 6 種の型にラベルを入れて描き、課題ごとの絵は持たない。(5) 案内役のキャラクター 1 体（ドット絵。FB2-6）を、診断の導入、正誤の返し、まとめと節目に出す。笑わない、責めない、催促しない、非表示にできる。課題集は 126 件を新しい型で全件書き直し、12-21 の版で初級を 14 件に足す。サーバーなし、登録なし、データはブラウザの中だけ、連続記録・ハート・広告なし、は変えない。
- いちばん強い反論：(a) 3 択は「正解を見抜くゲーム」になり、短答や自由記述より学習の効果が小さい（E-23 の Wikipedia の記述）。r11 の「読んで考えて書く」より浅くなるかもしれない。返し（説明）で害を減らすが、自作の問題の質しだい［推測］。(b) 図とキャラクターと 3 倍の本文に枠を使うと、v1 の件数が 210 から 126 に減り、一気に進める人が早く尽きる（7 の行3）。(c) キャラクターは対象の現役層に子どもっぽく映り（R-13）、Progate の「意味なし」（E-30）と同じ反応を招く。非表示の設定で受けるが、切った人の体験は r11 と同じになる。
- 作らない場合に起きること：Takuma の FB2 の 5 点に応えられず、「書き方とやり方がイマイチ」「合っていたか分からない」「文字だけで退屈」な体験のまま公開する。r11 の「答えを書く欄」は採点されず、未経験は自分の答えが合っているか知る手段がない。

## 10. やらないこと（非目標）と、はまりやすい所
- やらないこと（理由を1行ずつ）：
  - サーバー、アカウント、ログイン、端末間の自動同期：Takuma の決定（2026-10-29）。費用ほぼ0を保つ。端末間はファイルの書き出し・読み込みで代える。
  - Web Push と定時のリマインダー、脅すような通知、キャラクターによる催促：iOS ではホーム画面に追加した場合だけ届き（E-8）、サーバーなしでは予約配信ができない。脅す通知は Duolingo の通知への不満そのもの（E-13）。002 で決める（Q6 の決定 A）。
  - Service Worker によるバックグラウンドでの更新と通知：v1 の Service Worker は配布物のキャッシュ（AC-23）と新しい版への切り替え（AC-28）だけ。
  - ブラウザの中でのコードの実行（サンドボックス、実行環境つきのエディタ、自動採点）と、自由記述の AI 添削：実行環境と教材を抱える形になり、Progate、Mimo、freeCodeCamp と同じ土俵になる。添削はサーバーか LLM が要る（S-3）。初級は「動かす前の 10 分」。
  - 答えを書く欄（r11 の `answer`）：FB2-2 の「選択肢をタップする形」に合わせて外す。採点できないまま残すと「合っていたか分からない」（FB2-3）が残る。自由記述が要る学習は 002 以降（Q20）。
  - 難しすぎ・簡単すぎの自己申告：段階は正誤で動かす（S-11）。残すと規則が 2 系統になり、どちらが効いたか分からない（Q20）。
  - 同じ問題への 2 回目の回答（選び直し）、1 問ごとの時間制限、ヒント：選び直しは「当たるまで押す」になり、返しを読まなくなる［推測］。時間制限は圧（E-17）。ヒントは説明と二重になる（E-24 の hints は 002 の候補）。

## 11. 受け入れ条件
画面名と文言キーは designer が design/001-daily-learning.md で確定する。ここでは状態の名前と文言キーを仮に置く（`diagnosis.*`、`task.*`、`guide.*`、`history.*`、`settings.*`、`error.*`、`home.*`）。

状態の名前と遷移（r12 で FB2 に合わせて書き直した。変えていない行はそのまま）：
- 初めて開く → `diagnosis.start`（案内役のキャラクターが 1 回出る：AC-45）→ `diagnosis.question`（n / 3）→ `task.today`（課題が1件出ている）。iOS の Safari でスタンドアロン表示でないときは、`diagnosis.start` の画面に案内 `home.addToHomeScreen` を出す（AC-21）
- `task.today` の中（r12）：題名、導入（図つき）、1 問目 → 選ぶ → 返し（正誤と説明）→ 「次の問題へ」→ 2 問目 → … → 3 問目の返し → 「まとめへ」→ `task.rate`。ルートの要素に `data-task-question-index`（答えた問題の数 0〜3）と `data-task-question-total`（3）を出す。1 問の回答は 1 回で確定し、選び直せない（AC-41）。3 問目に答えた時点で課題は「完了」として履歴に移る（`report` が done、`score` が 0〜3、`answers` に 3 つの選択）。「まとめへ」を押さずに再読み込みすると `task.done`（役に立ったかは未回答）になり、まとめを表示した印は保存しない（r13。tech-lead r5 の要修正 2 の案 A。決定表 r13-1）。申告の値の名は契約どおり `done` で、`complete` は使わない（r13。決定表 r13-2）
- `task.rate`（まとめ。正答数、ひとこと解説、累計と祝い、役に立ったかを聞く）→ 答えるか、答えずにページを離れる → `task.done`。`task.rate` に閉じる操作を置くかは designer が決める。置くなら `task.rate.close` で、再読み込みと同じく「未回答」で `task.done` にする
- `task.today` で「今日はやめておく」（仮に `task.skip`。導入でも問題の途中でも押せる）→ `task.skipped`（`report` が no_time。途中まで答えていれば `answers` と `score` は答えた分だけ残る）。難しすぎ・簡単すぎの申告は置かない（r12。AC-7）
- `task.done` と `task.skipped` には「次の一手に進む」（仮に `task.next`）が 1 つある（r8。FB-2）。押すと、今の段階と診断に従って次の課題を同じ日に出し `task.today` になる。出す課題が尽きていれば `task.exhausted`。押さない限り次の課題は出ない（再読み込みしても `task.done` / `task.skipped` のまま）。1 日に進める数の上限はない
- 翌日（端末の日付が変わった後の最初の読み込みか操作）→ 自動で 1 件出して `task.today`。出す課題がなければ `task.exhausted`
- 日付をまたいだ回答はできない（r6 から。契約 contracts/data.md の 4）：画面を開いたまま端末の日付が変わった後の最初の操作は実行されず、前日の課題は申告のないまま `report` が none の行として履歴に移り（答えた分の `answers` と `score` は残る）、新しい日の課題が出る（AC-32）
- 段階の規則（r12。FB2-3。自己申告の「2 回連続」を正誤に置き換えた）：目標の領域の履歴のうち `report` が done の行だけを新しい順に見る（no_time と none の行は数えず、流れも切らない）。数えるのは今の段階と同じ `level` で出した課題だけで、段階が変わった後は新しい段階の行から数え直す（D10 と同じ）。下げる：直近 2 件の `score` がともに 1 以下なら段階を 1 つ下げる（「初」はそのまま）。上げる：直近 3 件の `score` がすべて 3 なら段階を 1 つ上げる（「上」はそのまま）。両方に当たることはない。段階の変化は「次に出す課題」から効き、表示中の課題は変わらない。変わったことは次の課題の `task.today` に 1 文（仮に `task.level.adjusted.down` / `.up`。責めない文言で、AC-45 の禁止語の対象）で知らせる
- 一度出した課題の ID は、申告の種類にかかわらず、再び出さない
- 段階は領域ごとに持つ（例：`levels: { backend: "中" }`）。診断は目標の領域の段階だけを設定し、他の領域の段階は保つ
- 診断のやり直し（r8）：まだ完了していない今日の課題（`task.today`）があれば、その課題はそのまま残り（ID は変わらない）、まとめの後に「次の一手に進む」で出す課題から新しい診断に従う。`task.done`、`task.skipped`、`task.exhausted` からやり直したときは、やり直しの直後に新しい診断に合う課題を同じ日に出す。`task.exhausted` からやり直して同じ領域と段階を選ぶと、再び `task.exhausted` になる
- 修了と進級（r8。FB-3）：`task.exhausted` は、目標の領域の今の段階の課題をすべて出し終えた状態。段階が上級でなければ「この段階を修了」の文言と「次の段階へ進む」（仮に `task.exhausted.advance`）を出し、押すとその領域の段階を 1 つ上げて同じ日に次の課題を出す。上級なら「この領域をすべて修了」の文言と「新しい課題は次の版で足す」を出す。どちらにも「別の領域を選ぶ」（診断のやり直し。`task.exhausted.redo`）がある。進級は正誤による段階の変化とは別で、数え直しの起点になる。注意：正答 1 以下が 2 件続いて段階が下がった先の組をすでに出し終えていると、`task.exhausted` で「次の段階へ進む」が出て、合わなかった段階に戻ることになる。仕様として許容し、画面の文は designer に任せる
- 進み具合（AC-36）：`task.today` の課題が、目標の領域と今の段階の中で何件目か（出した件数 + 1）と、その組の総数を出す。「出した件数」はその組で出した課題の数で、申告の種類を問わず、`report` が none の行も含む
- 今週（AC-37）：端末の日付で、月曜日から今日までの暦日。先週以前の完了日数を出す要素は置かない
- 累計（AC-35）：完了した課題の総数（統計の `data-stat-completed` と同じ値）。節目は 7、30、100 件で、数は変えない。累計の要素と祝いの要素の識別子、節目ごとの文言のキーは designer が決め、tech-lead が contracts/identifiers.md に書く
- 正誤の返し（AC-41）：各問の選択肢の要素は `data-choice-index`（0〜2）を持つ。答えた後は、問の要素に `data-answer-result`（correct / incorrect）、各選択肢に `data-choice-state`（selected-correct / selected-incorrect / correct / none）が付き、選んだ選択肢の説明の要素（仮に `task.question.explain`。`data-testid`。中身は課題集の `explain`）が 1 つ、不正解なら正解の選択肢の説明も 1 つ（合計 2 つ）見える。正誤は文言キー `task.answer.result.correct` / `.incorrect`（例：「正解」「惜しい」。designer が決める）と印でも示し、色だけに頼らない（WCAG 1.4.1）
- 正答数（AC-42）：`task.rate` と `task.done` の要素に `data-score`（0〜3）。履歴の行に `data-score`。点数や段位の文言（「点」「ランク」「レベルアップ」）は使わない
- 図（AC-44）：課題集の `figure` は `{ type, labels[], highlight?, alt }`。`type` は flow / layers / compare / sequence / tree / split の 6 つ（ID は tech-lead が contracts/identifiers.md に書く）。`labels` は型ごとの個数の範囲（9 の表）で各 1〜12 字、`alt` は 1〜80 字。画面の図の要素は `data-figure-type` を持ち、`role="img"` と `aria-label`（`alt` の値）を持つ。導入に 1 つ必ず、各問に任意で 1 つ。図は HTML と CSS（矢印などの小さな形だけインラインの SVG）で描き、図の要素の中に `<img>` を置かず、図のための画像ファイルを持たない。線の対比（AC-44）の測り方は (a) 図の部位に印（仮に `data-figure-part`：label / line / box）を置き、line の要素の計算済みの `stroke` か `border-color` と、図の要素の `background-color` を比べる。(b) design/tokens.md の図の色のトークン（ライト・ダークそれぞれの線、文字、背景）を数値で検査し、画面では文字だけ axe で見る、に替えるかは tech-lead と designer が G1 で決め、contracts/identifiers.md か design/tokens.md に書く（r13）
- キャラクター（AC-45）：要素は仮に `guide.character`（`data-testid`）で `data-mood`（idle / correct / incorrect / celebrate）を持ち、絵は `aria-hidden="true"`。絵はドット絵（FB2-6。原寸 32×32 か 48×48 の格子、色は 8 色以内、画面では原寸の整数倍に拡大し、PNG なら `image-rendering: pixelated`、SVG なら `shape-rendering: crispEdges` でぼやけさせない。具体の値は designer が決め、PNG のスプライトか SVG の path かは tech-lead が G1 の ADR で決める。既存作品の絵は使わない：17）。台詞は文言キー `guide.*`（各キーの値が 40 字以内。コードポイントで数える。en の 40 字＝約 7 語で足りるかは designer が G1 で確かめる：要確認）。出る場所は `diagnosis.start`（idle）、`task.today` の返し（各問。correct / incorrect）、`task.rate`（celebrate）、`task.exhausted`（celebrate）の 4 か所だけ。出ない場所は `diagnosis.question`、`task.today` の導入と未回答の問（1 問も答えていない `task.today` では `guide.character` が 0 件。答えると返しと一緒に出て、「次の問題へ」で次の問に進むと消える：r13、verifier r5 の要修正 1）、問題文と選択肢の要素（仮に `task.question`、`task.choice`）の中、`settings`、`history`、`error`。設定の `settings.character.show`（保存データ `showCharacter`、既定 true）で非表示にでき、非表示のときは `guide.character` が 0 件で、解説、累計、祝いは残る
- 読み込み：保存データがあるブラウザに正しいファイルを読み込むときは確認 `settings.import.confirm` を出し、確定すると既存のデータをファイルの中身で置き換える（結合しない）。版番号が今の版以下のファイルは今の形に移して読み、今より新しい版は拒む（AC-25）

## 13. 仮説と KPI
- 仮説：コードを書いたことがない人から現役のエンジニアまでが、図つきの説明と 3 択 × 3 問の課題を毎日完了し、やりたい日は続けて進めるようになる。公開を 2026-12-07 と仮置きし（r12 で 11-30 から動かした）、2027-01-04（公開28日後）までに、出した課題に対する完了率が「未計測」から 40% 以上になれば正しい（「完了」は 3 問目に答えた課題。同じ日の 2 件目以降も分母と分子に入る。本人が「次の一手に進む」を押した課題だけが分母に入るので、勝手に増えない）。
- 計測の手段：サーバーがないので、Q1 の決定は A「外部に送らない」。アプリが統計の画面（AC-24。13 の指標と1対1の 13 の値）を設定に持ち、URL を渡した利用者（Takuma と周りの5人程度。未経験の人を 1〜2 人加えられるかは Q14。Takuma の返事がないまま判定日になれば B とする。B のときは、経験年数が未経験の ID の利用者は、その人の値ごと集計から外す。誰が該当するかは聞き取りか書き出しファイルの `diagnosis.years` で知る。B なら該当者がいないので、6 の価値の行の「分けて見る」確かめは行わない）が判定日にその画面のスクリーンショットを指揮役に送る。verifier が集計して判定する。
- 「直近7日」は端末の日付で今日を含む 7 暦日、「今週」は月曜から今日まで（AC-24、AC-37）。
- 「初めて開いた日に1件目を完了した利用者の割合」の定義と母数（D9）：「初めて開いた日」は初回の診断の 1 問目を確定した日。母数は、判定日に統計の画面を送った利用者。
