# 第1部 発見（何を、なぜ作るか）

## 1. 紹介文
コードを書いたことがない人から現役のエンジニアまで、URL を開いて3問（1分以内）の自己診断に答えると、その日から毎日「今日やる学習」が1つ、15分以内（初級は10分以内）で終わる形で出ます。インストール、アカウント登録、料金はなく、ブラウザを開いてから最初の課題が出るまで2分以内です。96本の地図が並ぶ roadmap.sh や、積んだままの教材から「どれをやるか」を選ぶ時間が毎日0分になります。終えると、その課題でいちばん大事な「ひとこと解説」が開き、累計の件数が1つ増えます。時間がある日は「次の一手」で続けて進め、段階の課題をやり切ると次の段階へ進めます。難しすぎ・簡単すぎの申告が2回続けば次の課題から段階が変わります。連続記録を失う仕組み、ハート、広告、英語の壁はありません。課題の 8 割以上はこの画面の中で読む、考える、答えを書く、までが終わり（要る課題には「外で行う」の印）、書きかけの答えは残ります。入力したデータはあなたのブラウザの中だけに保存され、外には送りません（ページを配る GitHub Pages が接続の記録として IP アドレスを保存するだけです）。

## 2. 中心の Job
- Job ストーリー（1つだけ）：学びたい気持ちはあるが何から手を付けるか迷うとき（通勤の15分、休日にまとめて進めたい日のどちらも）、今の自分の段階に合った学習を1つずつ、迷わずに始めたい。そうすれば決められない日をなくし、毎日続けられる。
- 機能の面：段階に合う学習が1つ決まり、やりたい日はその場で次に進める。　気持ちの面：「今日も前に進んだ」と感じ、終えた直後に小さな発見がある。　人の目の面：同僚や面接で「最近学んだこと」を具体的に言える。

  - Sololearn との違い：段階に合わない課題を出さず、競争や広告でなく、累計と「ひとこと解説」で前に進んだ実感を作る。
  - Exercism と freeCodeCamp との違い：人のメンターや長いカリキュラムを待たせず、開いたその場で今日の1件が決まり、やりたい日は続けて進める。

## 4. 4つの力
| 今の状況の押し | 新しいものの引き | 乗り換えの不安 | 今の習慣 |
|---|---|---|---|
| 学ぶべきことが多すぎて、どれから手を付けるか決まらないまま日が過ぎる（E-1）。未経験には用語の壁（E-12）。コースは段階に合わない（E-3、E-4）。連続記録やハートが圧になる（E-13） | 診断3問、毎日1つ、15分（初級 10 分）。やりたい日は続けて進める。終えると解説と累計が増える。やり切ると次の段階へ。URL を開くだけ、登録なし、日本語、無料、失う仕組みなし | 「自己申告の診断で本当に合う課題が出るのか」「未経験なのに動かさずに身につくのか」「一気に進めたら課題が尽きるのでは」「ブラウザのデータが消えたら履歴も消えるのでは」「また続かないのでは」 | 気が向いたときに記事を読む、Progate を途中でやめる、Udemy を積む、ChatGPT に聞く、何もしない |

## 5. 機会と解決
- 根（成果）：出した学習に対する完了率
- 機会（顧客の言葉で）：

  - O-2 「自分の段階に合わない課題が出て、つまらないか、つらい」。未経験なら「用語も環境も分からない」（解き方：自己診断で決める／申告で動かす／テストで測る／本文で用語を説明する）
  - O-3 「始めても、翌日には忘れて続かない」（解き方：ホーム画面に置く／Web Push／カレンダー登録／連続記録／累計と節目）

## 8. 推奨
- 形を変えて作る：r7 の「診断と今日の学習」を土台に、3 点を足して作り直す。(1) 初級を未経験向けに書き直し（旧初級は中級へ）、診断の文言に領域の説明と「書いたことがない」の区分を足す。(2) 申告の後に「次の一手に進む」で同じ日に続けられ、段階をやり切ると「修了」として進級か別の領域を選べる。1 日の上限は置かない。(3) 完了の直後に「ひとこと解説」と累計・節目を見せ、今週の完了日を統計に出す。連続日数のカウンター、ハート、リーグ、脅す通知、ペットは入れない。サーバーなし、登録なし、データはブラウザの中だけ、は変えない。
- いちばん強い反論：(a) 未経験を「コードを動かさない 10 分」で迎えても、書いて動かす Progate や Mimo に勝てず、初級の 84 件を書く 1 週が無駄になる。(b) 連続記録を捨てるのは、Duolingo が公開している「7 日で翌日 2.4 倍」（E-14）の効き目を捨てることで、累計と今週の完了日で同じだけ続く証拠はない［推測］。(c) 同じ日に何件も進めると「毎日 15 分」の習慣の芯が薄れ、初日にやり切って燃え尽きる人が出るかもしれない（E-19 の分散学習は本文を確かめていない）。
- 作らない場合に起きること：r7 のまま公開しても Takuma の FB 3 点（初級の対象、一気に進めたい、面白さ）に応えられず、未経験の利用者には「すでにコードを書いているエンジニア向けです」の導入文で門前払いになる。一気に進めたい人は 1 日 1 件で離れ、終えた後の画面が「静か」なまま戻る理由がない。

## 9. やること
Kano の分類は［推測］。候補の RICE：S-1 の診断＋処方（Reach 四半期 30 人＝URL を渡す範囲［推測］、Impact 3、Confidence 50%、枠 3週）を採った。r8 で足した候補：S-5 続けて進む（Reach 30、Impact 2、Confidence 50%。FB-2）、S-6 解説と累計（Reach 30、Impact 2、Confidence 50%。FB-3）、S-7 修了と進級（Reach 30、Impact 1、Confidence 50%）。削った候補：連続記録（Reach 30、Impact 1、Confidence 50%。E-13、E-15 の副作用）、Web Push（Reach 10、Impact 2、Confidence 50%。E-8）、ペットとキャラクター（Reach 30、Impact 1、Confidence 25%。絵の工数が枠に入らない）。

- P-1「画面の中で終わる」：課題は、別のエディタ、端末、外部サイトに行かなくても、この画面の中で「読む → 考える → 答えを書く → 自己申告する」まで終えられる型を基本にする。コードは答えを書く欄に書いてよいが、実行と採点はしない（10）。外に出ないと終えられない課題は `external` として「外で行う」の印と要る道具を出し、各組（領域 × 段階）の 20% 以下に抑える（AC-29、AC-30）。初級の `external` は、この端末のブラウザだけで行えるもの（開発者ツールなど）に限る（AC-34）。
- P-2「楽に続く」：毎日 1 つは自動で出る（15分、初級は 10 分、登録なし）。やりたい日は申告の後に「次の一手に進む」で続けられ、上限は置かない（FB-2）。診断済みなら開いてから操作 0 回、2 秒以内で今日の課題が見え（AC-31、AC-15）、途中で閉じても書きかけの答えから再開できる（AC-32）。終えると解説と累計が増え（AC-35、AC-38）、連続日数や「途切れた」は見せない。効く指標は 13 の「直近7日に3日以上完了した利用者の割合」（目標 50%）と「2 件目以降の完了の割合」（目標 20%）、ガードレール「今日はできない」の申告率（30% 未満）。

## 11. 受け入れ条件
画面名と文言キーは designer が design/001-daily-learning.md で確定する。ここでは状態の名前と文言キーを仮に置く（`diagnosis.*`、`task.*`、`history.*`、`settings.*`、`error.*`、`home.*`）。

状態の名前と遷移（r8 で FB-2 と FB-3 に合わせて書き直した。変えていない行はそのまま）：
- 初めて開く → `diagnosis.start` → `diagnosis.question`（n / 3）→ `task.today`（課題が1件出ている）。iOS の Safari でスタンドアロン表示でないときは、`diagnosis.start` の画面に案内 `home.addToHomeScreen` を重ねて出す（AC-21）
- `task.today` で「完了」→ `task.rate`（役に立ったかを聞く。同じ画面にひとこと解説、累計、祝い）→ 答えるか、答えずにページを離れる → `task.done`。`task.rate` に閉じる操作を置くかは designer が決める。置くなら `task.rate.close` で、再読み込みと同じく「未回答」で `task.done` にする
- `task.today` で「難しすぎ」「簡単すぎ」「今日はできない」→ `task.skipped`
- `task.done` と `task.skipped` には「次の一手に進む」（仮に `task.next`）が 1 つある（r8。FB-2）。押すと、今の段階と診断に従って次の課題を同じ日に出し `task.today` になる。出す課題が尽きていれば `task.exhausted`。押さない限り次の課題は出ない（再読み込みしても `task.done` / `task.skipped` のまま）。1 日に進める数の上限はない
- 翌日（端末の日付が変わった後の最初の読み込みか操作）→ 自動で 1 件出して `task.today`。出す課題がなければ `task.exhausted`
- 日付をまたいだ申告はできない（r6 から。契約 contracts/data.md の 4）：画面を開いたまま端末の日付が変わった後の最初の操作は実行されず、前日の課題は申告のないまま `report` が none の行として履歴に移り、新しい日の課題が出る。書きかけの答えは none の行に残る（AC-32）
- 「連続」の定義（r8 で「申告は1日1回」の前提を外した）：同じ種類の申告（難しすぎ、または簡単すぎ）が、申告の履歴の新しい方から2件並ぶこと。日付は問わない（同じ日の 2 件でも並ぶ）。間に「完了」か「今日はできない」が入れば途切れる。`report` が none の行は申告でないので数えず、流れも切らない。数えるのは今の段階と同じ段階で出した課題への申告だけで、段階が変わった後は新しい段階の申告から数え直す（D10）
- 段階の変化は「次に出す課題」から効く（r8）：2 件目の申告の直後に「次の一手に進む」を押せば同じ日の次の課題が新しい段階になり、押さなければ翌日の課題が新しい段階になる。表示中の課題は変わらない
- 一度出した課題の ID は、申告の種類にかかわらず、再び出さない
- 段階は領域ごとに持つ（例：`levels: { backend: "中" }`）。診断は目標の領域の段階だけを設定し、他の領域の段階は保つ
- 診断のやり直し（r8 で「翌日から効く」をやめた）：まだ申告していない今日の課題（`task.today`）があれば、その課題はそのまま残り（ID は変わらない）、申告の後に「次の一手に進む」で出す課題から新しい診断に従う。`task.done`、`task.skipped`、`task.exhausted` からやり直したときは、やり直しの直後に新しい診断に合う課題を同じ日に出す（Task Issued は本人の操作でだけ増える）。`task.exhausted` からやり直して同じ領域と段階を選ぶと、再び `task.exhausted` になる
- 修了と進級（r8。FB-3）：`task.exhausted` は、目標の領域の今の段階の課題をすべて出し終えた状態。段階が上級でなければ「この段階を修了」の文言と「次の段階へ進む」（仮に `task.exhausted.advance`）を出し、押すとその領域の段階を 1 つ上げて同じ日に次の課題を出す。上級なら「この領域をすべて修了」の文言と「新しい課題は次の版で足す」を出す。どちらにも「別の領域を選ぶ」（診断のやり直し）がある。進級は申告による段階の変化とは別で、「連続」の数え直しの起点になる（段階が変わるので）
- 進み具合（AC-36）：`task.today` の課題が、目標の領域と今の段階の中で何件目か（出し終えた件数 + 1）と、その組の総数を出す
- 今週（AC-37）：端末の日付で、月曜日から今日までの暦日。先週以前のことは画面に出さない
- 累計（AC-35）：完了した課題の総数（統計の `data-stat-completed` と同じ値）。節目は 7、30、100 件（designer が文言を決める。数は変えない）
- 読み込み：保存データがあるブラウザに正しいファイルを読み込むときは確認 `settings.import.confirm` を出し、確定すると既存のデータをファイルの中身で置き換える（結合しない）。版番号が今の版以下のファイルは今の形に移して読み、今より新しい版は拒む（AC-25）
- スタンドアロン表示の判定は `navigator.standalone === true` か `display-mode: standalone`。iOS の Safari の判定は User-Agent による（tech-lead が G1 で確定済み）
- `navigator.storage.persist()` は、診断を終えて `task.today` を初めて表示した後に1回だけ求める（D6 により記録はしない）
- 領域と段階の値：領域は Q3 で決めた6つ、段階は初 / 中 / 上。ID は contracts/identifiers.md の 5（r8 で経験年数に 1 つ足す：AC-40）
- 「ネットワークへの送信は 0 件」の数え方（AC-12、AC-23）：Service Worker が返した応答を除いた要求と、失敗した要求の合計が 0 件
- 読み込みの流れ（AC-20、AC-25）：ファイルを選ぶ → 検査 → 保存データがあれば `settings.import.confirm` → 置き換え
- ホーム画面で初めて開いたときの案内 `home.standalone.import`（AC-22）は、保存データがない間は開くたびに出す
- 「直近7日」（13 の指標と AC-24）：端末の日付で、今日を含む 7 暦日
- 「初めて開いた日」（D9）：初回の診断の 1 問目を確定した日（端末の日付）。2 問目以降、やり直し、申告では変わらない。データの全削除の後に再び診断すれば、その日が新しい「初めて開いた日」
- 「2 件目以降の完了」（AC-24、13）：同じ端末の日付に完了した課題のうち、その日の 1 件目を除いた件数の合計
- 段階の規則の確かめ方（AC-8）：seed には「段階と、直近の 1 件を除く申告の履歴」を入れ、直近の 1 件は画面で申告する
- 設定、統計、履歴の画面の状態の名前は仮に `settings`、`settings.stats`、`history` と置く（designer が確定）
- 答えを書く欄（AC-32）：`task.today` に 1 つ。内容は課題の ID と日付に結び付けて保存し、同じ日の同じ課題でだけ復元する。申告のときに履歴の行へ移す（`answer`。空なら空文字列）
- 課題の型（AC-29、AC-30）：各件に `mode`（`in_app` / `external`）、`external` には `tools`（1 件以上）。`task.today` の要素に `data-task-mode` を出す。選ぶ規則は `mode` で変えない
- ひとこと解説（AC-38）：各件に `insight`（1〜120 字）。`task.today` では DOM に置かず、「完了」の後の `task.rate` と `task.done` でだけ出す（`task.skipped` では出さない）
- 「開いてから操作 0 回」（AC-31）の数え方：ページの読み込みが終わってから、クリック、タップ、キー入力を 1 回も行わずに `data-state` を読む。重なる要素は `role="dialog"` と `aria-modal="true"` の要素、`position: fixed` で課題の題名を覆う要素を数える

## 12. 非機能要件
すべての行に数字と測り方を付ける。
- 速さ：ページを開いてから課題の表示まで 2 秒以内（AC-15。遅い回線と CPU の制限の下、Chromium で 5 回）。診断の各質問の切り替えは 500 ミリ秒以内（AC-1 で 3 区間計る）。「次の一手に進む」から次の課題の表示まで 1 秒以内（AC-33）。初回の転送量は圧縮後の合計 150 KB 以下（contracts/budgets.md。課題集が 210 件と解説で増えるので、tech-lead が課題集の枠を見直す。合計は変えない。測り方：G3 では配布物の各ファイルを `gzip -9` で圧縮した大きさの合計を証拠に書く）。
- 続けやすさと完結（P-1、P-2）：診断済みなら開いてから課題が見えるまで操作 0 回（AC-31）かつ 2 秒以内（AC-15）。答えを書く欄は最後の入力から 1 秒以内に保存し、同じ日に開き直すと復元する（AC-32）。申告の後は 1 回の操作で次の課題が出る（AC-33）。課題集は各組で `external` が 20% 以下（AC-29）、初級は 10 分以下（AC-34）。診断から 1 件目の課題までは 2 分以内（紹介文。G4 で指揮役が実機で計る）。
- オフラインや通信エラーのとき：一度読み込んだ後は、ネットワークなしで画面の中の操作（次の一手に進む、修了、進級を含む）がすべて動き（AC-12）、再読み込みとホーム画面からの起動でも 3 秒以内に同じ状態が出る（AC-23）。配布物を新しい版に差し替えたときは、オンラインで 3 回以内の読み込みで切り替わる（AC-28）。
- セキュリティとプライバシー：扱う個人データは、自己診断の回答（目標の領域、自己評価、経験年数）、課題の完了と申告の履歴、答えの本文。すべてブラウザの保存（localStorage）に置き、ブラウザの外に送らない（AC-12、AC-23 で送信 0 件）。ページの配信元（GitHub Pages）は接続の記録として IP アドレスを保存する（E-10）。Q1 の決定は A なので、計測の送信はない。アカウントなし。Cookie なし。削除は AC-16。読み込むファイルは信頼できない入力として扱い、スキーマで検査して textContent で表示する。プライバシーの説明ページを docs/support/ に用意する（G5 の前）。
- 対応ブラウザ：Safari 17 以上（iOS、macOS）と Chrome の最新 2 版（Android、PC）。自動テストは Playwright の Chromium と WebKit。実機の Safari は G4 で確かめる。

## 13. 仮説と KPI
- 仮説：コードを書いたことがない人から現役のエンジニアまでが、毎日出る課題を完了し、やりたい日は続けて進めるようになる。公開を 2026-11-30 と仮置きし、2026-12-28（公開28日後）までに、出した課題に対する完了率が「未計測」から 40% 以上になれば正しい（r8 で「同じ日の 2 件目以降」も分母と分子に入る。本人が「次の一手に進む」を押した課題だけが分母に入るので、勝手に増えない）。
