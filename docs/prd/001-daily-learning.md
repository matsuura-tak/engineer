# 第1部 発見（何を、なぜ作るか）

## 1. 紹介文
すでにコードを書いているエンジニアが、URL を開いて3問（1分以内）の自己診断に答えると、その日から毎日「今日やる学習」が1つだけ、15分で終わる形で出ます。インストール、アカウント登録、料金はなく、ブラウザを開いてから最初の課題が出るまで2分以内です。96本の地図が並ぶ roadmap.sh や、積んだままの教材から「どれをやるか」を選ぶ時間が、毎日0分になります。英語の壁、ハート、広告はありません。難しすぎ・簡単すぎの申告が2回続けば次の日から段階が変わるので、同じ段階の課題を繰り返されることがありません。課題の 8 割以上は、読む、考える、答えを書く、自己評価する、までこの画面の中で終わり、別のエディタ、端末、外部サイトは要りません（要る課題には「外で行う」の印が付きます）。書きかけの答えは残るので、途中で閉じても続きから再開できます。入力したデータ（診断の回答と履歴）はあなたのブラウザの中だけに保存され、ブラウザの外には送りません（ページを配る GitHub Pages が、接続の記録として IP アドレスを保存するだけです）。

## 5. 機会と解決
- 根（成果）：出した学習に対する完了率
- 機会（顧客の言葉で）：
  - O-1 「何を学ぶべきか決められず、結局何もしない日が多い」（解き方：処方する／地図を見せる／AI に聞かせる）
  - O-2 「自分の段階に合わない課題が出て、つまらないか、つらい」（解き方：自己診断で決める／申告で動かす／テストで測る）
  - O-3 「始めても、翌日には忘れて続かない」（解き方：ホーム画面に置く／Web Push／カレンダー登録／連続記録）
  - O-4 「他で学んだことが、学習の計画に反映されない」（解き方：手入力／外部サービス連携）。002 以降に回す
- 選んだ機会と理由：O-1 を中心に、O-2 と O-3 を最小の手当てで支える。O-1 が根の指標に直接効き、競合の不満（E-1、E-2、E-6）が最も集中しているため。

## 8. 推奨
- 形を変えて作る：依頼どおり「診断と今日の学習」を、ブラウザだけで動く Web アプリとして作る。形を3つ変える。(1) 教材を抱えず、同梱した「15分の課題」を1つ処方する。(2) 生成 AI、トレンド取り込み、Web Push は v1 に入れず、002 以降でサーバーの要否と一緒に決める。(3) データはブラウザの中だけに置き、消える不安には書き出し・読み込みで手当てする。iOS の Safari では診断の前にホーム画面への追加を案内するが、ホーム画面の Web アプリは Safari と保存を共有しない（E-7）ので、引き継ぎは書き出し・読み込みの手作業になる。
- いちばん強い反論：ブラウザだけでは「続ける」仕組みが弱い。通知は v1 にない（iOS の Web Push はホーム画面に追加した場合だけ：E-8）ので翌日戻る動機は本人の習慣だけに頼る。さらに Safari は7日操作がないとデータを消し（E-7）、ホーム画面に移すにも、端末を変えるにも、本人がファイルを書き出して読み込む手間が要る。この2つが重なると、「続いた人の履歴だけ消える」最悪の形になり、完了率より先に継続が崩れる。これに加えて、課題の品質と量の問題は残る。Q2 で v1 を 126件（1日約25件）に減らしたが、残り 126件を公開後14日までに書いて配る約束が加わり、公開直後の2週に書く時間が要る。
- 作らない場合に起きること：対象の人は roadmap.sh や ChatGPT で毎回自分で選び続け、「決められない日」が残る。このアプリの以降の機能（他で学んだことの反映、トレンド）は土台がなく始められない。

## 10. やらないこと（非目標）と、はまりやすい所
- やらないこと（理由を1行ずつ）：
  - サーバー、アカウント、ログイン、端末間の自動同期：Takuma の決定（2026-10-29）。費用ほぼ0を保つ。端末間はファイルの書き出し・読み込みで代える。
  - Web Push と定時のリマインダー：iOS ではホーム画面に追加した場合だけ届き（E-8）、サーバーなしでは予約配信ができない。002 で決める（Q6 の決定 A）。
  - Service Worker によるバックグラウンドでの更新、バックグラウンド同期、「更新があります」の通知：v1 の Service Worker は配布物のキャッシュ（AC-23）と、配り直した新しい版への切り替え（AC-28）だけ。裏で取りに行く仕組みと通知は 002 以降。
  - ブラウザの中でのコードの実行（サンドボックス、実行環境つきのエディタ、自動採点）：実行環境と教材を抱える形になり、Mimo や freeCodeCamp と同じ土俵になる。P-1「画面の中で終わる」とはぶつからない：答えを書く欄（AC-32）にコードやテキストを書くことはできるが、実行も採点もせず、完了の目安と見比べて自己申告する。課題の型は 9 の (a)(b)(c) に限り、実行が要るものは `external` の印を付けて各組 20% 以下にする（AC-29）。r4 の「ブラウザの中でコードを書く・実行する」から書き直した。
  - 生成 AI による課題の生成：端末内 LLM は入れない（決定済み）。外部 API はサーバーが要る（S-3）。
  - トレンドの取り込みや、実行時にネットから別の JSON を取りに行く更新：v1 は配布物に同梱した JSON だけ。課題の追加は配布物ごと配り直す（AC-28）。002 以降で静的な JSON の配信を検討する。
  - 他で学んだことの記録と反映（O-4）：Job が2つ目になる。002 で扱う。
  - 6領域すべての自己評価：v1 は目標の領域だけ。診断を1分以内に収めるため（Q5 の決定 A）。
  - 連続記録（ストリーク）、ハート、広告、課金：競合の不満の中心（E-4、product.md）。
  - 課題の中身の自動採点：自己申告にする。実力テストは v1 で扱わない。
  - 英語の課題集：252件を2言語で書く時間がない（Q4 の決定 A）。画面の文言だけ英語を持つ（AC-26）。
  - iOS アプリと App Store への提出：Takuma の決定。出すときは product.md の「iOS 版を出すときに書く」を埋める。
- はまりやすい所と避け方：
  - 診断の質問を増やしたくなる：3問の上限を AC-1 に固定し、足すなら他を削る。
  - 課題集の件数が足りないまま出す：AC-4 で件数を数え、AC-10 で尽きたときの表示を用意する。公開後14日までに足す版が届かない：AC-28 で新しい版の切り替えを確かめ、配り直しの日を docs/progress.md に書く。
  - 「段階」の規則を複雑にしたくなる：2回連続の規則だけにし（AC-8）、変えるなら公開後の数字で決める。
  - 保存の方式を後から変えてデータを失う：保存の形式に版番号を付け、書き出しファイルと同じ形にする。読み込みは「今の版以下は移して読み、新しい版は拒む」（AC-20、AC-25）。
  - テストのつなぎ口（データの初期化、差し替え）を本番の配布物に残す：リンクを踏ませるだけで他人のデータを消せる。11 の冒頭の決まりに従い、reviewer が G2 で確かめる。
  - ホーム画面の案内を「データが守られる」と読ませる：案内の手順に「Safari のデータは引き継がれないので書き出して読み込む」を必ず入れる（AC-21）。
  - 「外で行う」課題を増やしたくなる（書きやすいため）：AC-29 で各組 20% 以下に固定し、超えるなら `in_app` に書き直す。
  - 答えを書く欄を必須にしたくなる、または答えを採点したくなる：任意のまま、採点しない（P-2。入力を強いると「今日はできない」が増える［推測］）。
  - 診断済みの人に、更新の知らせや案内を開いた直後に重ねたくなる：AC-31 で開いた直後の重なる要素を 0 件に固定する。

## 11. 受け入れ条件
画面名と文言キーは designer が design/001-daily-learning.md で確定する。ここでは状態の名前と文言キーを仮に置く（`diagnosis.*`、`task.*`、`history.*`、`settings.*`、`error.*`、`home.*`）。

状態の名前と遷移（verifier r1 の要修正3、4、5、verifier r2 の要修正と提案への答え）：
- 初めて開く → `diagnosis.start` → `diagnosis.question`（n / 3）→ `task.today`（課題が1件出ている）。iOS の Safari でスタンドアロン表示でないときは、`diagnosis.start` の画面に案内 `home.addToHomeScreen` を重ねて出す（AC-21）
- `task.today` で「完了」→ `task.rate`（役に立ったかを聞く）→ 答えるか、答えずにページを離れる（再読み込み、タブを閉じる）→ `task.done`（その日はもう課題が出ない）。`task.rate` に閉じる操作を置くかは designer が決める。置くなら `task.rate.close` で、再読み込みと同じく「未回答」で `task.done` にする
- `task.today` で「難しすぎ」「簡単すぎ」「今日はできない」→ `task.skipped`（その日はもう課題が出ない）
- 翌日（ブラウザの端末の日付が変わった後の最初の読み込みか操作）→ `task.today`。出す課題がなければ `task.exhausted`
- 日付をまたいだ申告はできない（上の規則の帰結。r6 で明記。契約 contracts/data.md の 4）：画面を開いたまま端末の日付が変わった後の最初の操作は実行されず、前日の課題は申告のないまま `report` が none の行として履歴に移り、新しい日の課題が出る。例：23:55 に出した課題を 0:05 に「完了」しようとすると、完了は記録されず（`task.rate` にも進まず）、その課題は none の行に移り、翌日の課題が `task.today` に出る。書きかけの答えは none の行に残る（AC-32）
- 「連続」の定義：同じ種類の申告（難しすぎ、または簡単すぎ）が、申告の履歴の新しい方から2件並ぶこと。間に「完了」か「今日はできない」が入れば途切れる。申告は1日1回だけなので、同じ日に2回目は起きない。`report` が none の行（申告のないまま日付が変わった課題）は申告でないので数えず、流れも切らない。数えるのは今の段階と同じ段階で出した課題への申告だけで、段階が変わった（診断のやり直しを含む）後は新しい段階の申告から数え直す（D10。契約 contracts/data.md の 5 の規則と同じ。例は AC-8 の 8 通り目と 9 通り目）
- 一度出した課題の ID は、申告の種類にかかわらず、再び出さない
- 段階は領域ごとに持つ（例：`levels: { backend: "中" }`）。診断は目標の領域の段階だけを設定し、他の領域の段階は保つ
- 診断のやり直し：その日にまだ課題を出していなければ、やり直しの直後に新しい診断に合う課題を出す。その日にすでに課題を出していれば（`task.today`、`task.done`、`task.skipped` のどれか）、やり直しても新しい課題は出さず、新しい診断は翌日の課題から効く（AC-5 の例外は作らない。Task Issued を同日に増やさない）。`task.exhausted` からやり直して同じ領域と段階を選ぶと、その日のうちに再び `task.exhausted` になる
- 読み込み：保存データがあるブラウザに正しいファイルを読み込むときは確認 `settings.import.confirm` を出し、確定すると既存のデータをファイルの中身で置き換える（結合しない）。版番号が今の版以下のファイルは今の形に移して読み、今より新しい版は拒む（AC-25）
- スタンドアロン表示（ホーム画面の Web アプリ）の判定は `navigator.standalone === true` か `display-mode: standalone`。iOS の Safari の判定は User-Agent による（tech-lead が G1 で確定。iPadOS の Safari は Mac の UA を送るので `navigator.maxTouchPoints > 1` を併用する案を検討する：tech-lead r2）
- `navigator.storage.persist()` は、診断を終えて `task.today` を初めて表示した後に1回だけ求める（15 の Storage Persist Answered の `track()` の呼び出し位置はこのとき。D6 により記録はしない）
- 領域と段階の値：領域は Q3 で決めた6つ（バックエンド設計、フロントエンド、データベース、インフラとクラウド、テストと品質、Git とチーム開発）、段階は初 / 中 / 上。`data-task-area` と `data-task-level` に入れる固定の ID は tech-lead が G1 で contracts/ に決める（表示名でなく ID で比べる）
- 「ネットワークへの送信は 0 件」の数え方（AC-12、AC-23）：ページが出した要求のうち、Service Worker が返した応答（Playwright の `response.fromServiceWorker()` が true）を除いたものと、失敗した要求（`requestfailed`）の合計が 0 件。Q1 の決定は A（外部に送らない）なので、除外する送信先はない
- 読み込みの流れ（AC-20、AC-25）：ファイルを選ぶ → 検査（版番号が今より新しいか形式が違えば `error.import.message` を出し、確認は出さない）→ 保存データがあれば `settings.import.confirm` → 置き換え。保存データがなければ確認を出さずに置き換える
- ホーム画面で初めて開いたときの案内 `home.standalone.import`（AC-22）は、保存データがない間は開くたびに出す（閉じた印は保存しない）。文言は Safari に限らず「別のブラウザで入力したデータは自動では引き継がれない」と書く
- 「直近7日」（13 の指標と AC-24）：端末の日付で、今日を含む 7 暦日
- 「初めて開いた日」（13 の指標、AC-19、AC-24 の `data-stat-first-open-date`。D9）：初回の診断の 1 問目を確定した日（端末の日付）。ページを開いただけの日や、案内 `home.addToHomeScreen` を閉じて診断を始めずに去った日は数えない。2 問目以降、診断のやり直し、申告では変わらない。データの全削除（AC-16）の後に再び診断すれば、その 1 問目の日が新しい「初めて開いた日」になる。読み込み（AC-20）ではファイルの値をそのまま使う（契約 contracts/data.md の 2）
- 段階の規則の確かめ方（AC-8）：seed には「段階と、直近の 1 件を除く申告の履歴」を入れ、直近の 1 件は画面で申告する。段階を申告のときに更新する作りでも、出すときに履歴から決め直す作りでも、同じ結果になる
- 設定、統計、履歴の画面の状態の名前は仮に `settings`、`settings.stats`、`history` と置く（designer が design/ で確定）
- 答えを書く欄（AC-32）：`task.today` に 1 つ（`data-testid` は仮に `task-answer`）。内容は課題の ID と日付に結び付けて保存し、同じ日の同じ課題でだけ復元する。申告の種類にかかわらず、申告のときに履歴の行へ移す（保存の形式と書き出しファイルに `answer` を持つ。空なら空文字列）
- 課題の型（AC-29、AC-30）：タスク集の各件に `mode`（`in_app` / `external`）を持ち、`external` には `tools`（文字列の配列、1 件以上）を持つ。`task.today` の要素に `data-task-mode` を出す。選ぶ規則は `mode` で変えない（`external` を後回しにしない。各組の中で同じ順序の規則で選ぶ）
- 「開いてから操作 0 回」（AC-31）の数え方：ページの読み込みが終わってから、クリック、タップ、キー入力を 1 回も行わずに `data-state` を読む。`task.today` の上に重なる要素は、`role="dialog"` と `aria-modal="true"` の要素、`position: fixed` で課題の題名を覆う要素を数える。AC-21（診断前のみ）と AC-22（保存データがないときのみ）はこの AC の Given（診断済み、スタンドアロンでない）では出ない

テストのつなぎ口（verifier r2 の W-1〜W-12 と tech-lead r1 の (e)。名前は tech-lead が G1 で contracts/ に確定する）：つなぎ口は本番の配布物に入れない。テスト用のビルドだけで有効にするか、テストのコード側（Playwright の addInitScript、setOffline、timezoneId、device による UA の偽装など）から差し込む。アプリの側に置くのは、画面の識別子（ルートの `data-state` と `data-build-version`、要素の `data-testid`、進み具合の要素の `data-question-index` と `data-question-total`）、課題の素性（`task.today` の要素の `data-task-id`、`data-task-area`、`data-task-level`、`data-task-mode`）、答えを書く欄（`data-testid`）、履歴の行（`data-task-id`、`data-date`、`data-report`、`data-helpful`）、統計の値（`data-stat-*`）、読み込み時間（`data-debug-load-ms`）、タスク集と書き出しファイルの JSON スキーマと置き場所、seed の形（保存の形式と同じ JSON）だけ。テストの側から差し込むもの：状態の初期化、時刻の固定と実行中に進める手段、配布物の差し替え（AC-28。静的サーバーのファイルを新しい版に置き換える）、データの投入（seed）、保存の失敗と `persist()` の拒否の注入、スタンドアロン表示と iOS Safari の偽装、通信の遮断と送信の件数の記録、対応ブラウザと実行環境（Chromium と WebKit）。

- AC-1：初めて開くと自己診断が始まり、3問で終わる
  - Given：保存データがない状態でページを開いた（iOS Safari の偽装なし）
  - When：読み込みが終わり、3問に順に答える
  - Then：状態 `diagnosis.start` が表示され、質問の総数が 3 で、各質問の画面に進み具合が「n / 3」（n は 1〜3）の形で出て、最後の質問の番号が 3 であり、「診断を始める」の操作から 1 問目が表示されるまでと、各質問で回答を確定してから次の質問が表示されるまで（1 問目 → 2 問目、2 問目 → 3 問目）の 3 区間が、いずれも 500 ミリ秒以内である。3 問目の回答を確定してから課題が表示されるまでは AC-2 の 1 秒で判定し、この AC では数えない（r7 で明記。上限の値は r6 と同じ）

## 12. 非機能要件
すべての行に数字と測り方を付ける（tech-lead r1 の要修正）。
- 速さ：ページを開いてから課題の表示まで 2 秒以内（AC-15。遅い回線と CPU の制限の下、Chromium で 5 回）。診断の各質問の切り替えは 500 ミリ秒以内（AC-1 で 3 区間計る：始める → 1 問目、1 問目 → 2 問目、2 問目 → 3 問目。3 問目 → 課題は AC-2 の 1 秒。契約 contracts/test-hooks.md「時間の計り方」の表と同じ）。初回の転送量は圧縮後の合計 150 KB 以下（tech-lead r1 の案。確定は contracts/。測り方：G3 では配布物の各ファイルを `gzip -9` で圧縮した大きさの合計を証拠に書く。公開後は本番の URL に `curl --compressed` で取った転送量の合計で確かめる）。
- 続けやすさと完結（P-1、P-2）：診断済みなら開いてから課題が見えるまで操作 0 回（AC-31）かつ 2 秒以内（AC-15）。答えを書く欄は最後の入力から 1 秒以内に保存し、同じ日に開き直すと復元する（AC-32）。課題集は各組で `external` が 20% 以下（AC-29）。診断から 1 件目の課題までは 2 分以内（紹介文。AC-1 の切り替え 500 ミリ秒 × 3 と AC-2 の 1 秒を含む。G4 で Takuma が実機で計る）。
- オフラインや通信エラーのとき：一度読み込んだ後は、ネットワークなしで画面の中の操作がすべて動き（AC-12）、再読み込みとホーム画面からの起動でも 3 秒以内に同じ状態が出る（AC-23。Service Worker）。配布物を新しい版に差し替えたときは、オンラインで 3 回以内の読み込みで切り替わる（AC-28）。
- セキュリティとプライバシー：扱う個人データは、自己診断の回答（目標の領域、自己評価、経験年数）、課題の完了と申告の履歴。すべてブラウザの保存（localStorage。確定は tech-lead の G1 の ADR）に置き、ブラウザの外に送らない（AC-12、AC-23 で送信 0 件）。ページの配信元（GitHub Pages）は接続の記録として IP アドレスを保存する（E-10）。Q1 の決定は A なので、計測の送信はない。利用者を 10 人以上に広げて B（GoatCounter）を足す場合だけ、15 のイベントを件数として送る（IP と UA は GoatCounter が受け取るが保存しない：E-11）。アカウントなし。Cookie なし。削除は AC-16。読み込むファイルは信頼できない入力として扱い、スキーマで検査して textContent で表示する（tech-lead r1）。プライバシーの説明ページを docs/support/ に用意する（G5 の前）。
- 対応ブラウザ：tech-lead が contracts/ に決める。推奨は Safari 17 以上（iOS、macOS）と Chrome の最新 2 版（Android、PC）。自動テストは Playwright の Chromium と WebKit。実機の Safari は G4 で Takuma が確かめる。

## 13. 仮説と KPI
- 仮説：すでにコードを書いているエンジニアが、毎日1つ出る課題を完了するようになる。公開を 2026-11-30 と仮置きし、2026-12-28（公開28日後）までに、出した課題に対する完了率が「未計測」から 40% 以上になれば正しい。
- 計測の手段：サーバーがないので、Q1 の決定は A「外部に送らない」。アプリが統計の画面（AC-24。13 の指標と1対1の 9 つの値）を設定に持ち、URL を渡した利用者（Takuma と周りの5人程度）が判定日にその画面のスクリーンショットを Takuma に送る。verifier が集計して判定する。
- 「直近7日」は端末の日付で今日を含む 7 暦日（AC-24 と同じ）。
- 「初めて開いた日に1件目を完了した利用者の割合」の定義と母数（D9、r6 で明記。目標 50% と 14 の線 25% は変えない）：「初めて開いた日」は 11 の冒頭のとおり、初回の診断の 1 問目を確定した日（端末の日付）。母数は、判定日に統計の画面を送った利用者（保存データのある人）。分子はそのうち `data-stat-first-day-completed` が true の人。ページを開いたが診断を始めずに閉じた人は、統計の画面がないので母数に含めない。その人の数は 6 の使いやすさの行の聞き取り（URL を渡した人のうち診断を終えた人の割合）で見る。
- 将来 B（GoatCounter などの匿名計測）を足す場合：利用者を区別できない（E-11）ので、出せるのは件数の比だけ。完了率（Task Completed ÷ Task Issued）、「役に立った」率、「難しすぎ」の申告率、「今日はできない」の申告率、Page Loaded の load_ms は出せる。利用者ごとの指標（初めて開いた日に完了した割合、直近7日に3日以上完了した割合、「データが消えた」の割合）は出せないので、B でも A の統計の画面と聞き取りで測る。
