# ADR 0002：保存は localStorage のキー 1 つ。形は版番号つきで書き出しと同じにし、ID は最初の公開から変えない

- 状態：提案（G1 で reviewer が判定する。2026-11-06 の改訂 2 に反論を出してもらう）
- 書いた役：tech-lead　日付：2026-10-30（2026-11-06 に改訂 2：FB 2 回目で保存の形を作り直し、formatVersion 1 のままにすると決めた。下の「改訂 2」。PRD r13、design r13。2026-11-05 に改訂：ID を凍結する時点を「最初の公開から」にし、公開前の課題 ID の付け替えと経験年数 `never` の追加を formatVersion 1 のまま行うと決めた。PRD r10、design r8）
- 関係する PRD、設計メモ、契約：docs/prd/001-daily-learning.md（r13。改訂 2 は AC-8、AC-19、AC-20、AC-23、AC-31、AC-32、AC-42、AC-45 も。r10 の時点では 9 の課題集の行、10 のはまりやすい所、11、12、AC-4、AC-40）、docs/adr/features/001-daily-learning.md、contracts/data.md、contracts/schemas/data.schema.json、contracts/identifiers.md の 5
- 元に戻す手間：大（利用者のブラウザにある保存データと、書き出したファイルを読み続ける必要がある）

## 背景
- サーバーがないので、正しいデータの置き場所は利用者のブラウザだけ。消えたときの手当ては書き出しと読み込みだけ（AC-19、AC-20、AC-25）。
- PRD は「保存の形式に版番号を付け、書き出しファイルと同じ形にする。今の版以下は移して読み、新しい版は拒む」と決めている（10）。
- AC-11 は「次の 1 回の書き込みだけ失敗させる」注入でテストする。
- origin（matsuura-tak.github.io）は、同じアカウントの他の Pages と共有する。
- design の U-5〜U-8 と U-11 は tech-lead に任された（G1 r1 の A で確定案を出した）。
- （2026-11-05 の改訂）Takuma の FB 1 回目（FB-1「初級＝未経験」）を受けた PRD r10 は、今の初級（書いている人向け）を中級の前半に移し、未経験向けの初級を新しく書く（9 の課題集の行、AC-4）。経験年数には「まだコードを書いたことがない」を足す（AC-40、design の D-41、U-16 の答えで ID は `never`）。PRD は「旧初級と旧中級の ID と並び順をどう付け替えるかは tech-lead が決める（公開前なので変えられる）」とする。
- まだ公開していない。`curl -sI https://matsuura-tak.github.io/engineer/` は 2026-11-05 も `HTTP/2 404`（確かめたこと）。公開は 2026-11-30 の仮置き（PRD 冒頭の時間の枠）。外に出た版 1 の読み手も、書き出したファイルも、まだない。

## 決定
- localStorage のキー `kyounoitte:data` 1 つに、schemas/data.schema.json の形の JSON を入れる。保存＝書き出し＝seed は同じ形（書き出しは `device` を除く）。1 回の保存は 1 回の setItem。
- `formatVersion`（今は 1）を持ち、スキーマは知らない項目を拒む。読み手が知らない項目か値を書く変更は必ず版を上げ、新しいアプリは古い版を移して読む。
- 領域、段階、経験年数、課題の ID は、最初の公開（2026-11-30 の仮置き）から変えない。公開の後は、課題は消さず、ID を使い回さず、足すことだけにする（identifiers.md の 5）。
- 公開前の今（2026-11-05）は、次の 2 つを formatVersion 1 のまま行う（G0 tech-lead r3 の 2 の案。前例は下の `firstOpenDate`）。
  - 課題 ID の付け替え（6 領域とも同じ）：旧初級 `<a>-beginner-001〜007` → `<a>-intermediate-001〜007`、旧中級 `<a>-intermediate-001〜007` → `<a>-intermediate-008〜014`、新しく書く初級 → `<a>-beginner-001〜014`、上級は `<a>-advanced-001〜007` のまま（2026-12-14 の版で `008〜014` を足す）。選び方（候補のうち ID が最も小さいもの。data.md の 5）は変えないので、中級は旧初級の課題から先に出る。並び順の項目は足さない。ID の形 `<領域>-<段階>-<3 桁>` とスキーマの検査も変えない。
  - 経験年数に `never` を足す（data.schema.json の years の enum。radio の並びの先頭。段階の規則には使わない）。
- 公開の時点で、その日の課題集の ID の一覧（ID と領域と段階）を固定し、足すことしか許さない単体テストを置く（下の「結果」。backend-engineer の仕事）。

## 改訂 2：FB 2 回目の保存の形（2026-11-06。formatVersion 1 のまま作り直す）

### 背景
- Takuma の FB 2 回目を受けた PRD r13 は、課題を「3 問 × 3 択で選んで学ぶ」型にし、答えを書く欄と「難しすぎ／簡単すぎ」の申告を外し、段階を正誤で動かす（AC-8：正答数が低い課題が 2 件続くと下げ、全問正解が 3 件続くと上げる）。案内役ミルを非表示にする設定を足す（AC-45）。
- 今の保存の形（下の「決定」と data.md の r10）は、行の `answer`（書いた答え、2,000 字まで）と申告 5 種（`done`、`too_hard`、`too_easy`、`no_time`、`none`）を前提にしている。r13 では意味のない項目になり、要る項目（答えた選択肢、正誤、正答数、段階が動いた事実、ミルの設定）がない。
- まだ公開していない（2026-11-06 23:08 JST に確かめた。下の「確かめたこと」）。公開は 2026-12-07 の仮置き（PRD r13 の冒頭。r10 の 11-30 から動いた）。外に出た版 1 の読み手も、書き出したファイルも、まだない。

### 決定
- `formatVersion` は 1 のまま、data.schema.json を r13 の形に作り直す（2026-11-05 の (e) と同じ扱い）。変えることは次のとおり（項目の名前と制約の細部は、次の回の data.md と data.schema.json で決める）。
  - `history` の行：`answer` を外す。`answers`（`{ choice, correct }` の配列、0〜3 件。`choice` は 0〜2 の選んだ位置、`correct` は答えたときの正誤）と `score`（0〜3。`answers` の `correct` が true の数と同じ）を必須にする。規則で段階が動いた `done` の行にだけ `levelChange`（`down` / `up`）を書く（D-60 の知らせを、推し量らずに保存した事実から決めるため。G1 tech-lead r3 の提案 6）。
  - `report` の値は `done`、`no_time`、`none` の 3 つ。`too_hard` と `too_easy` を外す。
  - `current`：`answers`（0〜2 件。1 問答えるごとに 1 回の setItem。AC-32）を必須にする。3 問目に答えたら `current` を外し、`done` の行（`answers`、`score`、あれば `levelChange`）と `levels` を 1 回の setItem で書く。
  - トップレベルに任意の真偽値 `showCharacter` を足す（ないときは true と読む）。`device` に入れない：読み込み（AC-20）は `device` だけこのブラウザの値を残すので、`device` に入れると読み込んだファイルの「非表示」が効かない（G0 tech-lead r5 の表、G1 tech-lead r3 の 3 の U-25）。
  - 正誤は答えたときに行へ書く。公開の後に課題の中身が直っても、統計（S9）と段階の規則の結果が変わらないようにするため（G0 tech-lead r5 の 2 の (2)）。
- 手元に残っている古い形の版 1 のデータ（2026-11-06 より前のアプリで作った、`history` か `current` を持つもの）は、新しいスキーマで弾かれて S0 error になる（`answer` は知らない項目、`answers` と `score` がない、`too_hard` と `too_easy` は知らない値）。S0 error の「そのまま書き出す」と「削除」で片付ける（data.md の 4）。黙って読み替えない（(d) を選ばなかった理由と同じ側）。
- `diagnosis`、`levels`、`device`、`firstOpenDate` だけのデータ（`history` が 0 行で `current` がない）は、形も意味も同じなので新しい形でも通る。
- 2,000 字の `answer.max`（下の「一緒に決めたこと」の U-6）と、答えの欄の `task.answer`（U-11）はこの改訂でなくなる。上限の見積もり（data.md の 10）は、1 行が数百字に縮むので次の回の data.md で書き直す（課題集の件数（v1 は 126 件、2026-12-21 の版で 168 件）の行でも WebKit の上限の 1 割未満の見込み［推測］）。

### 検討した案
| 案 | 良い点 | 悪い点 | 選ばなかった理由 |
|---|---|---|---|
| (i) formatVersion 1 のまま作り直す（採用） | 移す処理もそのテストも要らない。公開の最初の版が 1 で、契約に例外が残らない。古い形のデータは S0 error で止まり、黙って変わらない | 同じ版 1 なのに、2026-11-06 の前と後で形が違うデータが、公開前の手元（Takuma のブラウザ、古い見本と seed）にある。版 1 を 2 回作り直すことになり、「形を変えたら版を上げる」の決まりの例外を 2 度使う | — |
| (ii) formatVersion 2 にして、1 から 2 へ移す | 決まりどおり。古いデータの履歴を残せる | 書いた答え（自由な文字）から、選んだ選択肢と正誤と正答数は作れない。移すなら行を捨てるか、`score` のない行を許す例外を 2 の形に足すしかない。どちらも、得をする利用者が 0 人（未公開）なのに、公開後もずっと残る | 移せない情報を移すふりになる |
| (iii) formatVersion 2 にして、版 1 は読まない（S0 error） | 「形を変えたら版を上げる」を守る。古いデータは (i) と同じく止まる | 「版 1 は読まない」の分岐とその見本と単体テストが公開後も残る。data.md の 6 の「古い版は 1 版ずつ移して読む」に例外が入る | (i) と結果（手元の古いデータは削除で片付ける）が同じで、契約に例外を 1 つ足すだけ（2026-11-05 の (h) を選ばなかった理由と同じ） |
| (iv) 形を変えずに足すだけ（`answer` と 5 種の申告を残し、新しい項目を任意で足す） | 古いデータもそのまま読める | 使わない項目と値がスキーマに残り、seed と見本と単体テストがそれを持ち続ける。`too_hard` の行を段階の規則でどう読むかを決める必要。`score` のない行が残り、S9 の数え方が分岐する | 公開前に消せるものを、公開後は消せない形で残す |

### いちばん強い反論と、それでも選んだ理由
- 反論：版 1 の作り直しは 2 回目で、「形か意味を変えたら必ず版を上げる」という決まりが、公開前という理由で 2 度破られた。3 度目もあり得るし、Takuma の手元で古い形のデータが S0 error になると、Takuma が「データが壊れた」と受け取る。版を上げておけば、エラーの理由（古い版）を文言で示せる。
- それでも選んだ理由と手当て：
  - 版を上げても、手元の古いデータは削除するしかない（(ii) は移せない、(iii) は読まない）。違いは、エラーの文言が「古い版」か「読めない」かだけで、その差のために公開後も残る例外を契約に足さない。
  - 古いデータを持つのは Takuma の確認用のブラウザだけで、数えられる。2026-11-05 の (e) と同じ手当てを G3 の前に行う：2026-11-06 より前のアプリを開いたすべてのブラウザとホーム画面の Web アプリで、設定の「すべてのデータを削除」を押す（S0 error になっていれば、S0 の削除）。確かめは、削除の後に使い始めてから書き出したファイルに `"answer"` の項目と `too_hard`、`too_easy` の値がないこと。指揮役が docs/progress.md の G3 の前提に書き、Takuma に伝える。
  - 見本（contracts/fixtures/ の data と seeds）は次の回で r13 の形に作り直す。受け入れテストの seed と単体テストは verifier と backend-engineer が G2 で作り直す。
  - 3 度目を防ぐため、見直す条件に「公開の後は必ず版を上げる」を残し、公開の時点で ID と語彙を固定する単体テスト（下の「結果」）に `report` の 3 値も入れる。

### 見直す条件（改訂 2）

- Takuma の手元で、削除の後も古い形のデータが残っていた（書き出しファイルに `"answer"` がある）。

## 一緒に決めたこと（design の未決）
- U-5：S0 の error を採る。条件は data.md の 4（保存先が使えない、JSON.parse の失敗、スキーマ不一致、版が新しい）。部分だけ読むことはしない。
- U-6（2026-11-06 の改訂 2 でなくなった。書く欄がない）：答えの上限 `answer.max` は 2,000 字。答えが日本語か英数字（JSON で 1 字のままの字）なら、365 日分でも保存データは 1,000,000 字以下（791,179 字）で、測った localStorage の上限（Chromium 5,242,865 字、WebKit で日本語を含むと 2,621,432 字）に入る。改行、タブ、`"`、`\`、制御文字の多い答えでは長くなる（字の種類ごとの長さの表と上限は contracts/data.md の 10）。
- U-7：やり直しの診断の回答はメモリだけに持ち、「診断を終える」で 1 回だけ保存する。終える前に離れたら（やめる、nav、アプリ名、再読み込み）下書きを捨て、元の診断のまま（data.md の 2）。初回の診断は質問ごとに保存する（AC-11）。
- U-8：ID は design の値のまま（`backend` … `git`、`beginner` / `intermediate` / `advanced`、`lt1` … `gte5`、課題は `<領域>-<段階>-<3 桁>`）。2026-11-05 に経験年数の先頭へ `never` を足し、課題の番号を上の「決定」のとおり付け替えた（形は同じ）。
- U-11（2026-11-06 の改訂 2 でなくなった）：答えの欄の `data-testid` は `task.answer`。
- 「保存データあり」は、診断を終えたか履歴が 1 行以上（data.md の 3）。
- 段階は申告を保存するときに変え（data.md の 5）、`levels` に持つ。書き出しに「領域ごとの現在の段階」が入る（AC-19）。
- 申告の「完了」の値は `done`（verifier G0 r3 の W-8 案の `completed` ではなく、design と PRD AC-32 の `none` に合わせた）。
- `firstOpenDate`（統計の「初めて開いた日」）は、保存データが「なし」の状態で初回の診断の 1 問目を確定する保存で書き、以後変えない。`device` だけの保存（案内を閉じた印、persist の印）では書かない。そのためスキーマでは、`diagnosis` と `levels` が空で `history` が 0 行のときだけ省ける（data.md の 2 と 3。pdm の G1 の確認：iOS の Safari だけ案内を閉じた日が初日になり、first-day-completed が他のブラウザとずれるのを防ぐ）。v1 はまだ配っていないので、版は上げない（前の形で通った見本 18 件は、今の形でも合否が同じ）。

- `persist()` は、保存データで初めて今日の課題を出した後に 1 回だけ求め、求め直さない（PRD 11 の冒頭。U-14 は指揮役の決定 2026-11-04。data.md の 11）。印 `device.persistRequested: true` は、印がないときに今日の課題を作る保存に含める（setItem は 1 回のまま）。結果（`persistGranted`）は書かない。結果を書く別の保存を置くと、印のない「あり」のデータの起動で保存が 2 回になり、data.md の 2 の「最大 1 回」と食い違うため。設定の注意は S8 を描くたびに `persisted()` で今の状態を読む（design の D-31）。`persistGranted` はスキーマに残し（消すと前の実装で作った保存データが「読めない」になる）、アプリは書かない。形を変えないので `formatVersion` は 1 のまま。

## 検討した案
| 案 | 良い点 | 悪い点 | 選ばなかった理由 |
|---|---|---|---|
| (a) localStorage のキー 1 つ（採用） | 読み書きが同期で、状態の決め方が単純。書き出しが文字列そのまま。AC-11 の注入が setItem 1 つで済む。全体が通るか落ちるかの 2 択 | 1 origin あたりの上限がある（測った値は data.md の 10：Chromium 5,242,865 字、WebKit で日本語を含むと 2,621,432 字。本物の Safari 17 は未確認）。毎回全体を書く。同じ origin の他のページから読める | — |
| (b) IndexedDB | 大きい。非同期で画面を止めない。項目ごとに書ける | 非同期の手順と移し方（onupgradeneeded）が増える。書き出しには組み立てが要る。失敗の注入が難しい | 答えが日本語か英数字なら 365 日分でも 791,179 字（data.md の 10 の表）で、(a) の大きさの利点が要らない |
| (c) localStorage の複数のキー（診断、履歴、今日を別々に） | 書く量が減る | 2 つのキーの書き込みの間で失敗すると、ちぐはぐな状態が残る。版をキーごとに持つ必要 | 「1 回の保存＝1 回の setItem」が崩れ、AC-11 と壊れたデータの扱いが難しくなる |
| (d) 知らない項目を無視する緩いスキーマ（版を上げずに足す） | 足すだけなら古いアプリも読める | 古いアプリが書き出すと、知らない項目が黙って消える | データが黙って消えるより、「読めない」と言って止まる方が直せる |

## いちばん強い反論と、それでも選んだ理由
- 反論：localStorage は Safari の 7 日の消去の対象で、同じ origin の他のページから読み書きでき、上限も確かめていない。IndexedDB の方が「ちゃんとした」置き場所ではないか。
- それでも選んだ理由：7 日の消去は IndexedDB も同じ対象で、手当ては書き出しと読み込みしかない（PRD 7 の行 2）。origin の共有は置き場所を変えても同じ（ADR 0005）。大きさは、答えが日本語か英数字なら 365 日分で 791,179 字で、測った上限の WebKit（日本語を含むと 2,621,432 字）の約 3 割、Chromium（5,242,865 字）の約 15%（data.md の 10）。一度出した課題は二度と出さない（AC-6）ので、同じ日に続けて進めても（AC-33）、`history` の行数は課題集の件数（210 件、のちに 252 件）が上限になる。252 行がすべて日本語 2,000 字の答えでも約 545,000 字（252 ×（2,000 + 約 160））で、WebKit の上限の約 21%（G0 tech-lead r3 の 2。前の版の「約 3.3 年で上限」の心配は、課題集が約 1,200 件を超えるまで起きない）。単純さを優先し、上限に近づいたら (b) に移す。

- 付け替え（(e)）への反論：Takuma の確認用のブラウザとテストの見本には、古い ID の版 1 のデータが残る。古い `levels: beginner` は、新しい課題集では「未経験」の意味で読まれ、同じ版 1 のデータの意味が黙って変わる。これは (d) を選ばなかった理由（黙って変わるより止まる方が直せる）と同じ種類の危険ではないか。
- それでも選んだ理由と手当て：意味が変わるデータは公開前の手元にしかなく、数えられる。
  - G3 の前に、2026-11-05 より前のアプリを開いた、使ったすべてのブラウザとホーム画面の Web アプリ（iOS の Safari、ホーム画面に追加した Web アプリ、Mac の Safari と Chrome など。ホーム画面の Web アプリは Safari と保存を共有しない：PRD の E-7）で、設定の「すべてのデータを削除」を押す（Takuma が押す。指揮役が docs/progress.md の G3 の前提に書き、伝える）。
  - 確かめ：置き場所ごとに、削除の後に使い始めてから S8 の書き出しファイルを作り、旧 ID の `*-beginner-*` の行（2026-11-05 より前の日付の `history` の行と `current`）がないことを見る。旧 ID の行が 1 つでも残っていれば、その置き場所でもう一度削除する。
  - 見本（contracts/fixtures/ の data と seeds）は G1 で新しい ID の意味で作り直した（コミット c2a19ba、a608b71、0406818。2026-11-05 の check-schemas で 52 件が期待どおり）。受け入れテストの seed（backend/tests/acceptance/seeds/）と単体テストは verifier と backend-engineer が G2 で作り直す。
  - 公開の後は (f) が正しい手順になる。公開の時点で ID の一覧を固定するテストを置き、同じことが二度と起きない形にする。

## 結果
- 楽になること：保存、書き出し、seed、見本が 1 つのスキーマで検査できる。テストの注入が単純。
- 難しくなること、守り続けること：
  - 版を上げるたびに、1 版ずつ移す手順と、contracts/fixtures/data/v<n>/ の見本を足し、古い見本を読み続ける単体テストを残す。
  - 最初の公開から、課題の ID と語彙を変えない。課題集を直すときは中身を直し、ID は変えない。
  - 公開の時点で、backend-engineer が単体テストを 1 つ置く：その日の課題集の ID の一覧（ID、領域、段階）をテストの中に書き写して固定し、今の tasks.json がその一覧をすべて同じ領域と段階で含む（足すのは許し、消す、付け替える、段階を変えるのは落とす）ことを確かめる。語彙（領域 6、段階 3、経験年数 5（`never` を含む）、申告 3（2026-11-06 の改訂 2 で 5 から 3）、役に立ったか 3、`levelChange` 2、ミルの表情 4）も同じテストで固定する。公開の日（2026-12-07 の仮置き。改訂 2 の時点）の前の最後のビルドで作る。このテストがあることを G4 の reviewer の確認項目にする（指揮役が G4 の委任指示書に「ID と語彙を固定する単体テストがあり、今の tasks.json で通る」を入れる。なければ要修正）。
  - 公開前に ID をもう一度変えるなら、この ADR の (e) と同じ手当て（Takuma のデータの削除と見本の作り直し）が要る。
  - 保存データが「なし」か「診断の途中」の起動では setItem を呼ばない（AC-11 の注入はこの状態で行う）。「あり」の起動では data.md の 2 のとおり最大 1 回（日付が変わった課題を `none` の行に移す、今日の課題を出す。AC-6、AC-32）。画面を開いたまま日付が変わった後の操作で判定をやり直すときも同じ 1 回で、書きかけの答えもこれに含める（data.md の 4。2026-11-04）。他のキーに触らない。
- 元に戻すとき（(b) に移す）：新しい版のアプリが localStorage を読んで IndexedDB に移し、キーを消す。書き出しの形は変えない。3〜5 日と、移す手順のテスト。

## 見直す条件
- 公開の日が動いた、または公開の後に ID を変えたくなった（公開の後は (f) の手順で版を上げる。固定のテストを外して済ませない）。
- 保存データの文字列が 1,000,000 字（ブラウザの上限の推定の約 1/5）を超える利用者が出た、または QuotaExceededError の報告が 1 件でも来た。
- 「データが消えた」の報告が 30% 以上（PRD 14 の撤退基準）。
- 端末の間で自動で同期したい、またはサーバーを持つと決めた（002 以降）。
- 上限に届いたあとの扱い（QuotaExceededError のときの文言、古い行の答えを捨てる操作、IndexedDB への移行）は v1 では手当てせず、002 以降の課題とする（2026-11-03、指揮役の決定。Takuma から承認を委任されている：docs/approvals/delegation.md）。上限に届いても前に保存した値は残る（data.md の 10）。上の 1 行目の条件に当たったら、002 でこの 3 つを決める。
