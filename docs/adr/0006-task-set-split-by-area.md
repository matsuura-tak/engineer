# ADR 0006：課題集は 6 領域のファイルに分け、診断の 1 問目の確定で先に取り、「診断を終える」で待つ

- 状態：提案（G1 で reviewer が反論を出す。指揮役の仮の決定 2026-11-06 を受けて書いた）
- 書いた役：tech-lead　日付：2026-11-06
- 関係する PRD、設計メモ、契約：docs/prd/001-daily-learning.md（r13。9 の課題集の行、11 の「組のファイルを貯め終える前のオフライン」、12、AC-8、AC-10、AC-15、AC-23、AC-28、AC-44）、design/001-daily-learning.md（r13。D-61、S2、S10、5.1 の #47、#56、#74）、docs/adr/features/001-daily-learning.md、contracts/budgets.md の 1、contracts/service-worker.md の 3、contracts/test-hooks.md の W-4（どれも次の回で書き直す）
- 元に戻す手間：中（ファイルの名前と SW の FILES と予算の数え方が変わる。保存データの形は変えないので、利用者のデータの移行は要らない）

## 背景
- 今は課題集 1 つ（`./data/tasks.json`）を先読みして初回に全部読む。r10 の型の 210 件で gzip 後 69,313 バイト（2026-11-06、`check-budget.mjs`）。
- PRD r13（FB 2 回目）は 1 件に導入、3 問、選択肢 9 つの説明、図の指定を持つ型にした。1 つのファイルのままだと、初回が約 215 KB になり、PRD 12 の 150 KB を守れない（G0 tech-lead r5 の 4。Q24 の B を退けた根拠）。そこで Q24 の A「課題集を分けて初回 150 KB を守る」が決まり、分け方を G1 の ADR に任された（delegation.md 2026-11-05 の Q20〜Q27）。
- 指揮役は 2026-11-06 に「6 領域に分ける」を仮に決めた（delegation.md）。design r13 の D-61 はこの前提で書かれている。
- 制約：本番の依存 0、同じ origin の静的なファイルだけ（`connect-src 'self'`）、Safari 17 以上、AC-15（開いてから 2 秒、見直しの線 1,600 ms）、AC-23（一度読み込んだ後はオフラインで動く）、「次の一手に進む」から 1 秒。

## 決定
- 課題集を領域ごとの 6 ファイル `./data/tasks-<領域>.json`（`backend`、`frontend`、`database`、`infra`、`testing`、`git`）に分ける。1 ファイルに 3 段階すべてを入れる。`./data/tasks.json` はなくす。
- 取る時機（D-61）：(1) 診断の 1 問目（領域）を確定した時点で、その領域のファイルを裏で取り始める。「診断を終える」（`diagnosis.finish`）はその読み込みを待つ。失敗していたら `diagnosis.finish` と `task.next.retry` が取り直す。(2) 保存データありの起動では、`diagnosis.area` のファイルを起動の最初に取る。(3) S10 は、履歴にある別の領域のファイルを取る。`task.next` と `task.exhausted.advance` はファイルを取り直さない。
- SW の FILES は 6 ファイルすべてを含む（差し引き +5）。予算は「初回に読む分」と「SW が貯める分」の 2 つの枠に分ける（数字は次の回の budgets.md の 1）。

## 中身（契約は次の回で書く。ここでは方針だけ）
- ファイルの形：tasks.schema.json を新しい型にし、1 ファイルは 1 領域の課題だけを持つ。読み込んだ後に、手書きの検査で「すべての課題の ID の `<領域>` がファイル名の領域と同じ」を確かめ、違えばそのファイルは読めないものとして扱う（S2 は `error.tasks.offline` ではなく S0 error。どちらにするかは data.md と strings.md で決める）。
- 読み込みの仕組み（backend-engineer が作る）：領域から Promise を引く表を 1 つメモリに持つ。同じ領域は 1 回だけ取る。失敗した Promise は表から外し、次の呼び出しで取り直す。`fetch('./data/tasks-<領域>.json')` は SW を通る（あれば cache から返る）。`cache: 'reload'` は付けない。
- 1 問目の答えを「前へ」で変えたら、新しい領域のファイルを取り始める。古い領域の取得は止めない（S10 で使えることがある）。
- 失敗の扱い（D-61）：
  - S2：3 / 3 のまま、radio の回答を保ち、保存せず、`error.tasks.offline` と `task.next.retry` を出す。統計の出した件数は増えない。
  - S10：行を消さず、題名の代わりに ID と `history.row.unavailable` を出す（`data-title-unavailable="true"`）。
  - 保存データありの起動で `diagnosis.area` のファイルが取れないとき：SW が全部を貯め終えた後はこれは起きない（FILES に入る）。貯め終える前のオフラインの起動の扱いは、次の回の data.md の 4 と service-worker.md で決める（未解決 1）。
- index.html の preload：領域は HTML を書く時点では分からないので、課題集の `<link rel="preload">` は置かない（文言の 2 つは今のまま）。G0 の spike（tech-lead r5 の 4：課題集の先読みを外して後から取る形で 904〜930 ms）が、この形で AC-15 に余裕があることを示している。
- ビルド：build.mjs は 6 ファイルをすべてスキーマに通し、FILES に入れる。受け入れテストの差し替えの口（今の `--tasks <tasks.json>`、W-4）は、領域ごとのファイルを差し替えられる形に直す（名前は次の回の test-hooks.md。backend-engineer が build.mjs を直す）。
- AC-23 の 3 通り目は「やり直しの診断で別の領域へ移る `diagnosis.finish`」と読む（PRD :233 と AC-23 の Given が読み替えを認めている。G1 tech-lead r3 の要修正 2）。

## 検討した案
| 案 | 良い点 | 悪い点 | 選ばなかった理由 |
|---|---|---|---|
| (a) 6 領域のファイル（採用） | 段階が変わっても（AC-8 の規則、AC-10 の進級）同じファイルの中で済み、取り直しがない。S7 の判定（`seenNext`、`nextDone`）もそのファイルの中で決まる。オフラインの抜けが S2 と S10 の 2 か所に減る（D-61）。FILES は +5 | 1 ファイルが大きい：新しい型で約 30,000〜32,000、スキーマの上限いっぱいで約 50,000（G1 tech-lead r3 の 8 の見込み［推測］）。初回に読む量が (b) より約 +20 KB、AC-15 が約 +100 ms の見込み［推測。G2 で実物を計る］ | — |
| (b) 領域 × 段階の 18 組 | 1 ファイルが小さい（約 10,700。G0 tech-lead r5 の合成で測った最大）。初回が最も軽い | 段階が変わるたびに別のファイルが要る。SW が貯め終える前のオフラインで、規則で段階が変わった後の `task.next`、`task.exhausted.advance`、S7 の判定、S5 / S6 の操作がどれも失敗し得る（G1 tech-lead r3 の要修正 2 の (4)(5)）。それぞれにエラーの状態と文言とテストが要る。FILES は +17 | 状態と失敗の場所が 3 倍に増え、そのどれもが「貯め終える前のオフライン」という稀な場合のためにある |
| (c) 1 つのファイルのまま（今の形） | 道具も取る時機も今のまま。オフラインの抜けがない | 初回が約 215 KB で、PRD 12 の 150 KB を守れない。AC-15 は約 1.55 秒の見込みで、見直しの線 1,600 ms とほぼ同じ（G0 tech-lead r5 の 4） | PRD の非機能要件を守れない（Q24 の B として退けた） |
| (d) 1 つのファイルで、初回だけ要る領域を別に持つ（初回用 6 ファイル＋全部入り 1 ファイル） | 初回は軽く、2 回目からは 1 つのファイルで済む | 同じ課題を 2 か所に持ち、SW が貯める量がほぼ 2 倍。どちらを読むかの分岐が増える | (a) より複雑で、得がない |

## いちばん強い反論と、それでも選んだ理由
- 反論：分けるなら細かい方 (b) が初回の目標（150 KB、2 秒）に強い。(a) は 1 ファイルが大きく、後の版で課題を足すたびに初回が重くなる。しかもオフラインの抜けは「SW が貯め終える前」の短い時間にしか起きないので、(b) の状態の増え方はテストを足せば済む。
- それでも選んだ理由：
  - (a) でも初回は約 74,000〜92,000 の見込み（esbuild でまとめる形。G1 tech-lead r3 の 8［推測］）で、枠 150,000 の 6 割前後に収まる。168 件の版（2026-12-21）で 1 ファイルが 3 割増えても枠の中［推測］。
  - (b) で増える失敗の場所は、段階が変わった直後という、利用者がいちばん「進んだ」と感じる場面に重なる。そこで「ファイルをまだ取り込めていません」と出るのは、AC-8 と AC-10 の体験を壊す。(a) は失敗の場所を、まだ課題を始めていない S2 と、見返しの S10 に限れる。
  - 受け入れテストも、(b) では 5 か所のオフラインの状態を作る手順が要り、(a) では 2 か所で済む（D-61、5.1 の #47、#56、#74）。

## 結果
- これで楽になること：初回の転送量の枠に余りができる。段階の変化と進級でネットワークを使わない。失敗の状態が 2 つに決まる。
- これで難しくなること、守り続けること：
  - 1 ファイルの大きさを予算で見張る（次の回の budgets.md の 1 で「課題集の 1 ファイル」の枠を決め、check-budget.mjs が最大のファイルで数える。check-budget.mjs の直しは backend-engineer）。
  - 予算が 2 つの枠になる。初回に読む分（殻、文言、アイコンと manifest、ミルの 1 枚、課題集の最大の 1 ファイル）と、SW が貯める分（FILES の全部）。初めての訪問では SW が同じファイルをもう一度取るので、実際の通信は増える（service-worker.md の 7）。
  - 課題集を足す版では、領域ごとのファイルにだけ足す。ID と領域の対応（identifiers.md の 5）はこれまでどおり変えない。
- 元に戻すときの手順と手間：(b) に移すなら、ファイルの名前、FILES、取る時機、失敗の状態を足し直す。2〜3 日。(c) に戻すなら 150 KB の枠を変える PRD の決定が要る。

## 見直す条件
- 課題集の最大の 1 ファイルが gzip 後 40,000 バイトを超える、または初回に読む分が 130,000 バイト（枠の約 87%）を超える。
- AC-15 の 5 回の最大値が 1,600 ms を超える（ADR 0001 の見直しの線と同じ）。
- 1 領域の課題が 60 件を超える版を出す（v1 は 126 件で 1 領域 21 件、2026-12-21 の版で 168 件、1 領域 28 件：PRD r13 の Q22）。
- 貯め終える前のオフラインの失敗（S2 の `error.tasks.offline`）の報告が、公開後 1 件でも来る。

## 確かめたこと
- 今の課題集（r10 の型、210 件）を領域ごとに分けた gzip 後の大きさ（2026-11-06、tech-lead、node の zlib の level 9。新しい型ではない参考の値）：backend 35 件 12,525、frontend 12,624、database 12,360、infra 12,571、testing 11,962、git 12,252、1 つのファイル 69,313。
- 課題集の先読みを外して後から取る形の読み込みの時間：G0 tech-lead r5 の 4 の spike（遅延 150 ms、下り 1.6 Mbps、CPU 4 倍）で 919, 917, 904, 909, 930 ms。
- 新しい型の 1 ファイルの大きさ（約 30,000〜32,000、上限いっぱいで約 50,000）は G1 tech-lead r3 の 8 の見込みで、実物は未確認（課題集 v3 の下書きの後に、pdm の下書きを backend-engineer が写した時点で check-budget.mjs が数える）。
- 未確認：Safari 17 の実機での AC-15（これまでどおり G4 で Takuma が見る）。
